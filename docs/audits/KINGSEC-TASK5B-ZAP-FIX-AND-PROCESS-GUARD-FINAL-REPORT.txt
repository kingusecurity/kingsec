PRIORITY 1 — the read side. ZAP has never returned a finding until now.
--------------------------------------------------------------------------------

Fixed in `ZapScannerAdapter._read_findings()` (zap.py): reads and parses
the `-quickout` FILE, never `result.stdout` (which only ever carried a
"Writing results to <path>" line). Success requires three things, each
with a distinctly named failure reason: the file exists, is non-empty,
and parses as ZAP-shaped JSON (a dict with a `"site"` key). `returncode`
is never trusted alone - verified empirically that `-cmd` can exit 0
while reporting a real configuration error with no output file at all.
The file is deleted in a `finally` block after every scan, success or
failure, so it never accumulates in the data directory - confirmed live
(see PROOF below): the `scanner-output` directory was empty immediately
after a real scan completed.

Tests (`TestFileBasedSuccessCheck`, `TestOutputFileCleanup`,
test_zap_plugin.py): exit 0 with no file is FAILED, not a zero-findings
success; a real ZAP JSON file parses into findings with the right
titles; empty file, malformed JSON, and valid-but-wrong-shaped JSON are
each FAILED with a distinct reason; a genuine `{"site": []}` clean scan
remains a legitimate success; cleanup happens on both the success and
failure paths.

Logged in docs/STATUS.md as recurring-defect-class instance eight - the
most consequential form of the pattern found this engagement: every real
ZAP scan this product has ever run, in any environment, silently
returned zero findings while logging a clean "scan completed."


--------------------------------------------------------------------------------
PRIORITY 2 — the Job Object guard. Affects all nine scanners.
--------------------------------------------------------------------------------

Implemented exactly as specified in `SubprocessCommandRunner` (runner.py):

  - `stdin=subprocess.DEVNULL` unconditionally, every invocation, both
    platforms.
  - Windows: every scanner process is assigned to a Job Object created
    with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. On timeout, closing the
    job's last handle kills the ENTIRE tree, not just the process Python
    holds a handle to.
  - POSIX: `start_new_session=True` at process creation; on timeout,
    `os.killpg(os.getpgid(pid), SIGKILL)` instead of `Popen.kill()`.
  - ctypes, not pywin32: the four kernel32 calls needed
    (CreateJobObjectW, SetInformationJobObject, AssignProcessToJobObject,
    CloseHandle) are directly reachable from `ctypes.WinDLL` with
    correctly declared `argtypes`/`restype`. pywin32 would add a real
    third-party dependency to wrap four function pointers this module
    can bind itself - nothing about the task needs what pywin32 would
    add beyond that.
  - Every Windows-only branch is written as the literal
    `sys.platform == "win32"` comparison (never a derived boolean),
    matching the established pattern in `licensing/parser.py` - this is
    what lets mypy's Linux-pinned platform config (`pyproject.toml`,
    matching CI) prove the branch unreachable and skip it, the same
    accepted, already-documented trade-off as that file.

Test-count impact: +4 new tests, one new file
(`tests/integration/scanner/test_runner_process_supervision.py`), using
the exact parent/grandchild reproduction built during the hang
investigation:

  - `test_timeout_returns_quickly_not_after_the_grandchilds_own_sleep` —
    VERIFIED FAILING against the pre-fix code (120.2s, reported in the
    prior round's investigation); now asserts elapsed < 15s. This is the
    literal repro from the investigation, turned into a permanent
    regression test.
  - `test_no_grandchild_process_survives_the_timeout` — asserts on the
    real OS process table (`wmic`/`ps`), not the exception.
  - `test_scanner_reading_stdin_gets_eof_immediately` — a script that
    reads stdin must get 0 bytes immediately, not block.
  - `test_child_becomes_its_own_session_leader` (POSIX-only, skipped on
    this Windows dev machine, runs for real in CI's Linux container per
    the same platform pin referenced above) — verifies
    `os.getsid(0) == os.getpid()` inside the child, i.e. that
    `start_new_session` genuinely took effect, not just that nothing
    crashed.

All four new tests pass on this host (3 pass, 1 correctly skipped as
Windows-only-inapplicable) in 7.7s total - the same scenario that took
120+ seconds before this fix.


--------------------------------------------------------------------------------
PRIORITY 3 — -cmd as a code-level default.
--------------------------------------------------------------------------------

`_HEADLESS_FLAG = "-cmd"` is prepended unconditionally in
`ZapScannerAdapter._build_args()`, immediately after the resolved binary
path, before any operator-configured `scan_args`. Since `scan_args` is
purely additive by construction (it can only ever add elements to the
argv list this class builds, never remove one), there is no
configuration path that can strip it.

Tests (`TestHeadlessFlagIsNeverStrippable`, test_zap_plugin.py): `-cmd`
present with default `scan_args`; present even when the operator sets
unrelated `scan_args` (`-daemon -port 8090`); appears immediately after
the binary at a fixed position.

Two items logged, not chased, per instruction:
  - `-cmd`'s exit-code honesty on failure modes beyond the one verified
    (the unwritable-directory case, which exits 0 despite reporting a
    real error).
  - Whether `-cmd` suppresses every GUI path under flag combinations not
    currently used by this codebase (only `-quickurl`/`-quickout` were
    tested).
Priority 1's file-based success check covers the product against both,
regardless of how they eventually resolve.
