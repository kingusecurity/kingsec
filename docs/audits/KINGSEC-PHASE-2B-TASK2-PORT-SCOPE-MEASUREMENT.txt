2a. RE-TESTING THE FLAG CONFLICT PROPERLY
================================================================================

Exact command, exact output, run on this machine's real nmap 7.99:

    $ nmap --top-ports 1000 -p 18080 -n 127.0.0.1

    Starting Nmap 7.99 ( https://nmap.org ) at 2026-09-12 12:36 +0500
    Nmap scan report for 127.0.0.1
    Host is up (0.0010s latency).

    PORT      STATE  SERVICE
    18080/tcp closed unknown

    Nmap done: 1 IP address (1 host up) scanned in 0.54 seconds
    Exit code: 0

No error. -p wins cleanly - exactly 1 port scanned (confirmed via XML
scaninfo: numservices="1"). Reversing the order, and adding -sV -n to
match KingSec's real scan_args, gave the identical result four times:

    nmap --top-ports 1000 -p 18080 -n ...          -> numservices=1
    nmap -p 18080 --top-ports 1000 -n ...          -> numservices=1
    nmap -sV -n --top-ports 1000 -p 18080 ...      -> numservices=1
    nmap -sV -n -p 18080 --top-ports 1000 ...      -> numservices=1

This CONTRADICTS what I reported last round as a blanket "unpredictable"
finding. Re-investigating why: the earlier finding was real, but it was
specific to what VALUE -p carries, not to combining the two flags in
general. Isolated it precisely, reproduced each case multiple times:

    -p <single port>              + --top-ports  -> -p ALWAYS wins
    -p <port>,<port> (two singles)+ --top-ports  -> -p ALWAYS wins
    -p <port>,<range> (a dash-range anywhere in the list) + --top-ports
                                                   -> --top-ports ALWAYS wins
    -p <range only>                + --top-ports  -> --top-ports ALWAYS wins

Order on the command line never mattered in any of these; only whether
-p's value contains a numeric RANGE (a "-") does. This is exactly why my
first attempt (a range default, "1-1000") behaved unpredictably when
combined with --top-ports, and why 18080 alone did not - I conflated the
two cases into one blanket claim last round without re-testing the
specific single-port case. Corrected here, with the evidence shown, not
just re-asserted.

Practical consequence: nmap --top-ports 1000 -p 18080 <host> IS usable,
reliably, for a single explicit port. It is NOT usable if I also want a
literal port RANGE in the same -p value - which is exactly why the
revised design below never puts a range into the same -p as the explicit
port; see 2c.

2c. TWO-INVOCATION MERGE OPTION - EVALUATED, NOT YET IMPLEMENTED
================================================================================

Checked what merging would actually require by reading nmap_parser.py's
parse_nmap_xml() directly, not assuming:

  - Only OPEN ports ever produce a Finding at all (nmap_parser.py:101-102:
    "if port_state != 'open': continue" - closed/filtered ports are
    already silently dropped before a Finding is ever built).
  - Each open-port Finding has a structured, parseable title:
    f"Open port {portid}/{protocol}" (nmap_parser.py:118) - portid is
    right there in the title string, not buried in free text.

CONCLUSION: the merge is CLEAN, not messy. Two separate nmap invocations,
two separate parse_nmap_xml() calls, concatenate the two Finding lists,
and de-duplicate on the (portid, protocol) pair extracted from each
Finding's own title before returning - a small, independently-testable
post-processing step, not XML surgery or cross-invocation state tracking.
Deduplication is only needed for the rare case where the URL's explicit
port ALSO happens to fall inside nmap's own default top-N (both
invocations would then independently report the same open port).

Cost, measured on this machine: the default -sV scan (1000 ports) took
13.27s; a single-port -sV scan is a small fraction of that (well under a
second of actual port-probing work, dominated by -sV's per-open-port
service-detection cost, which only applies to the few open ports found
either way). The second invocation adds real subprocess-launch overhead
and a second nmap process spin-up, but not a second full 1000-port sweep
in wall-clock terms - it prevents the URL's own port from ever being
missed at negligible added cost.

RECOMMENDATION
--------------------------------------------------------------------------

1. Non-URL targets (IP_ADDRESS, HOSTNAME, NETWORK): NO -p, NO change from
   today. resolve_port_specification() already returns None for these -
   this is what it should continue to do; the REGRESSION was in
   NmapSettings.host_port_range's default reaching every target type
   through the settings layer, not in the per-target-type gating logic
   itself, which was already correct. Licensing-clean per your
   reasoning: nmap reads its own bundled/updatable data file on the
   operator's machine to pick these ~1000 ports; KingSec never touches,
   copies, or redistributes that file.

2. URL targets: two invocations, merged, per 2c above.
     Invocation A: settings.scan_args + no port flag at all -> nmap's own
       real default (~1000 ports, whatever nmap itself decides).
     Invocation B: settings.scan_args + -p <the URL's single explicit
       port> -> guarantees that exact port is always checked, using the
       flag-behavior confirmed safe in 2a (a single port in -p, no range,
       never contends with anything since invocation A carries no
       port-selector flag to conflict with).
     Merge: concatenate both invocations' parse_nmap_xml() results,
     de-duplicate by (portid, protocol).

3. KingSec's own 61-port list (nmap_default_ports.py) is NOT deleted, but
   its role changes: it is no longer nmap's port selection for anything.
   Docstring/comment updated to state plainly it is currently unused by
   the live scan path, kept as a documented, deliberately-curated floor
   for a future case (e.g., an environment where nmap's real default
   port data is unavailable or needs to be overridden for a licensing/
   sandboxing reason not present today) - not deleted outright, since it
   is real, reviewed work with a legitimate documented rationale, but its
   docstring must stop implying it is the operative default, since it no
   longer is once this design lands.

4. port_specification recording (bullet 3 of the blocking section):
     - Non-URL targets: None, unchanged (nmap's own default was used;
       nothing for KingSec to claim credit for or disclose beyond "no
       explicit port constraint was applied").
     - URL targets: a string that says what actually happened, honestly,
       e.g. "nmap's own default port selection, plus explicit port 18080"
       - NOT a list of numbers, since KingSec does not know and must not
         claim to know which ~1000 ports nmap's own default actually used
         on the machine that ran it (that's exactly the licensed data
         KingSec doesn't possess). Task 4's disclosure text should say
         "nmap's own default scan range plus the target's explicit port"
         for a URL target, not enumerate ports it cannot verify.

Not yet implemented. Files this would touch when approved: nmap.py
(resolve_port_specification()/_build_args() split into two invocations
for URL targets, a merge/dedupe helper), NmapSettings (host_port_range's
role and default reconsidered per point 3), nmap_default_ports.py
(docstring correction), the plugin wrapper (still calls resolve_port_
specification() for ScannerResult.port_specification, now returning the
descriptive string above for URL targets), and the regression test
(asserts the merge behavior and the explicit-port guarantee, not a fixed
literal port list).
