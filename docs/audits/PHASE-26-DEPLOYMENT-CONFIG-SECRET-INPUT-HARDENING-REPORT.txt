4. FINDINGS
================================================================================

Finding 1 [TESTED, CONFIRMED DEFECT — security-relevant]: An empty
`KINGSEC_JWT__SECRET_KEY` was silently accepted by both `Settings()` and
`create_wired_application()` in every non-production environment
(development, testing). This is a genuine, confirmed operational defect
distinct from "forgeable authentication": PyJWT itself refuses to sign with
an empty HMAC key (`InvalidKeyError: HMAC key must not be empty`), so the
practical effect was not silent forgeability but a deployment that starts up
looking healthy and then crashes uncaught the first time anything attempts
to issue a token (login, refresh, etc.) — "configuration values that appear
valid but are operationally unusable," precisely one of this phase's own
primary-objective categories. See Section 8, Objective 2 analysis.

Finding 2 [TESTED, CONFIRMED DEFECT — error-quality, not security]: An empty
`KINGSEC_SECRETS__API_KEY_PEPPER` was already correctly rejected (fail-closed
was never broken) by `HmacApiKeyHasher`'s own constructor, but as a bare
`ValueError` ("API key pepper must not be empty") with no environment
variable name and no remediation — inconsistent with every other secret
error in this codebase and with this phase's own Objective 5 criteria.

Finding 3 [TESTED, CONFIRMED DEFECT — error-quality, not security]: An
empty, malformed, or wrong-length `KINGSEC_SECRETS__ENCRYPTION_KEY` was
already correctly rejected (fail-closed was never broken) by
`FernetEncryptionService`/`cryptography.fernet.Fernet`'s own constructors,
but as a bare `ValueError` (e.g. "Fernet key must be 32 url-safe
base64-encoded bytes.") with no environment variable name and no
remediation — same category as Finding 2.

Finding 4 [TESTED, CONFIRMED DEFECT — documentation, first-run experience]:
`.env.example` documented `KINGSEC_STORAGE__DATABASE_URL` as a way to
"override DATA_DIR for PostgreSQL/external DB," implying it configures the
running server. It does not: `StorageSettings` has no `database_url` field
at all (confirmed by direct model introspection), and setting this variable
makes `Settings()` — and therefore the actual running application,
`python -m kingsec` — refuse to start with `ConfigError: storage.database_url
... Extra inputs are not permitted`. The variable is real, but is read only
by the Alembic migration CLI (`kingsec/alembic/env.py`, via a raw
`os.environ.get()` call that bypasses `Settings` entirely) as an override
for where migrations run, independent of what the server itself connects to.
A first-run operator following the old comment verbatim would find
migrations succeed against their intended database, then the server itself
refuses to start — a confirmed, reproducible first-run trap.

Finding 5 [TESTED, NOT A DEFECT]: trailing/leading whitespace in a secret
env var value is preserved verbatim, not stripped, by `Settings`/pydantic-
settings. This is correct, expected behavior for a secret field — silently
mutating a secret's bytes would be a worse footgun than preserving them
exactly as configured, since a signing key must be byte-identical across
process restarts for both signing and verification. Investigated per
Objective 3's explicit request; found to be working as intended, not
changed.

Finding 6 [TESTED, NOT A DEFECT]: cross-referencing every `KINGSEC_*`
variable name mentioned in `.env.example` against a live introspection of
`Settings.model_fields`'s nested groups found exactly one mismatch (Finding
4, above) and no other incorrect names, typos, or non-existent fields.
Approximately 70 real, accepted field paths exist that `.env.example` does
not mention at all (mostly `integrations.*` and `performance.*` groups) —
this is a documentation-completeness gap, not a correctness defect (nothing
is misdocumented, simply not all optional settings are illustrated), and per
this phase's own "do not solve unrelated findings" / "do not make cosmetic
changes unless they prevent an actual operational mistake" instruction, it
was not touched.

Finding 7 [TESTED, NOT A DEFECT — Docker/production scope]: none of the
above JWT/pepper "empty value" gaps were ever reachable through
`docker compose up`, because `docker-compose.yml` hardcodes
`KINGSEC_APP__ENVIRONMENT=production` unconditionally (re-confirmed
unchanged this phase), and production's own pre-existing 32-byte minimum-
length guard in `settings.py` already rejects an empty string (length 0)
before anything else runs. This mirrors the identical scope finding Phase 25
made about the placeholder gap. The encryption-key error-quality fix
(Finding 3) is NOT environment-gated and does apply inside Docker in
principle, but could not be demonstrated inside an actual running container
this phase — see Section 11's limitation on `git archive HEAD`.

5. ROOT CAUSE
================================================================================

Findings 1–3 share one root cause: prior to this phase, the only place in
the entire codebase that ever compared a JWT secret or API-key pepper
against a known-bad value was `Settings._guard_default_secrets_in_production()`,
gated to `environment=production`, and it only ever checked for the literal
placeholder string and a minimum byte length — it never checked for an empty
string as its own explicit, named case, and it never ran in any other
environment. Separately, `FernetEncryptionService`/`HmacApiKeyHasher`'s own
constructors DID already validate their inputs (this was never a fail-open
security gap), but nothing at the call site translated their raw
`ValueError`s into this codebase's established `ConfigError` convention —
`register_secrets()` (`infrastructure/secrets/provisioning.py`) only ever
wrapped the *missing* case, added no exception handling around the
`FernetEncryptionService(...)` construction itself, and `register_api_key_auth()`
(`infrastructure/auth/provisioning.py`, Phase 25) only checked for the
placeholder, not emptiness, before calling `HmacApiKeyHasher(...)`.

Finding 4's root cause: `KINGSEC_STORAGE__DATABASE_URL` was implemented, at
some point, as a raw-environment-variable override read directly by the
Alembic bootstrap script (`kingsec/alembic/env.py::_resolve_database_url()`)
for migration-only convenience, entirely independent of the `Settings`/
`StorageSettings` pydantic model the running server actually uses. The
`.env.example` comment was written as though this were a general,
server-wide override, which it has never been.

[TESTED throughout, via direct code reading of settings.py, models.py,
provisioning.py (both), fernet_encryption_service.py, api_key_hasher.py,
alembic/env.py, database.py, and empirical reproduction of every case in
Section 8's matrix.]

6. EXACT CHANGES MADE
================================================================================

(a) `src/kingsec/infrastructure/auth/provisioning.py`:
    - `register_auth()`: added a second, distinct check —
      `if not jwt_secret: raise ConfigError(...)` — immediately after the
      existing (Phase 25) placeholder check, before constructing
      `JWTTokenService`. Message names `KINGSEC_JWT__SECRET_KEY`, states it
      is empty, and gives the same generation command as the placeholder
      error. This is deliberately NOT a minimum-length policy: production's
      own 32-byte minimum is untouched, and a short non-empty synthetic
      secret (e.g. a single character) is still accepted in non-production,
      preserving the existing test-suite convention of short synthetic
      secrets (verified by a dedicated test, Section 7).
    - `register_api_key_auth()`: added the equivalent
      `if settings is not None and not pepper: raise ConfigError(...)`
      check, before constructing `HmacApiKeyHasher`. Without this, the
      function would still fail-closed (via `HmacApiKeyHasher`'s own
      `ValueError`) — this only upgrades the exception type and message,
      it does not change what is accepted or rejected.

(b) `src/kingsec/infrastructure/secrets/provisioning.py`:
    - `register_secrets()`: the `FernetEncryptionService(encryption_key)`
      construction is now wrapped in `try/except ValueError`, re-raising as
      `ConfigError` with the offending variable name, the underlying
      library's own (already-generic, value-free) message embedded for
      precision, and the standard generation command. Covers empty,
      malformed, and wrong-length key material uniformly — all three
      previously surfaced as the same undifferentiated bare `ValueError`
      class, now all become one consistent, well-formed `ConfigError`.
      Does not change which values are accepted (`Fernet`'s own validation
      logic is untouched) — only the exception type and message.

(c) `.env.example`:
    - Corrected the `KINGSEC_STORAGE__DATABASE_URL` comment block (Finding
      4): removed the implication that it configures the running server;
      states plainly that it is Alembic-migration-only, is not a `Settings`
      field, and that setting it will make the server refuse to start.
      Cross-referenced the existing `ALEMBIC_DATABASE_URL` section.
    - Added one clarifying line to the `KINGSEC_STORAGE__DATA_DIR` comment
      stating it is the only database location the running server itself
      honours, for the same reason.
    - No secret-value lines, defaults, or examples were altered — only
      explanatory comments.

Design rationale: every change was placed at the exact call site already
established by Phase 25 (the composition-root provisioning functions) or,
for Finding 3, the one other provisioning function with the identical
"validate a required secret before constructing a security-sensitive
service" shape. No new configuration framework, no new validation layer, no
change to `Settings`'s own pydantic validators, no change to which
environments are checked. This directly follows Objective 3/13's
constraints ("do not redesign the architecture," "do not introduce a new
configuration framework") and Objective 2's explicit instruction not to
impose an arbitrary minimum length.

10. SECURITY IMPLICATIONS
================================================================================

- Closes a genuine, confirmed reliability/security-adjacent gap: an empty
  JWT secret no longer allows a non-production deployment to start up
  looking healthy while being unusable (and would have crashed uncontrolled)
  the moment authentication was actually exercised. [TESTED, Section 8.]
- The API-key-pepper and encryption-key fixes are error-quality
  improvements only — fail-closed behavior for empty/malformed/wrong-length
  values was never broken before this phase, and is unchanged after it.
  [TESTED, Section 8 — same REJECTED outcome, different exception type.]

  length check, the placeholder rejection (Phase 25), and every production-
  environment behavior are byte-for-byte unchanged (Section 3, Section 8).
- No error message introduced or modified in this phase includes the actual
  secret/key value — verified directly by a dedicated test
  (`test_error_never_contains_the_key_value`) and by manual inspection of
  every new message string. All new messages name only the environment
  variable, state what is wrong in plain language, and give a concrete
  generation command — matching Objective 5's explicit criteria.
- The `.env.example` documentation fix (Finding 4) prevents a scenario where
  an operator could reasonably believe they had configured an external
  database when they had not; it does not change any accepted/rejected
  value and does not weaken any check.
- No secret value, encryption key, or generated test credential was printed
  to any log, terminal, report, or intermediate file during this phase. The
  disposable `.env` used for Docker Scenario C was deleted immediately after
  use.
