synthetic `.env` setting `KINGSEC_APP__ENVIRONMENT=development` while
`docker-compose.yml`'s own `environment:` block hardcodes
`KINGSEC_APP__ENVIRONMENT=production`. The rendered effective configuration
showed `production` — Compose's `environment:` block always wins over
`env_file:` for the same key, confirmed empirically, not merely inferred
from documentation. This is the actual precedence: (highest) explicit
`Settings()` init args > process environment variables (including anything
Compose's `environment:` block injects) > `.env` file (including anything
Compose's `env_file:` block injects, at the same environment-variable layer
docker-compose itself resolves before the container ever starts) > model
defaults. Inside a container, pydantic-settings' own dotenv-file loading
(`env_file=".env"` in `Settings.model_config`) finds nothing, because no
literal `.env` file exists inside the image (`git archive HEAD` never
includes a gitignored file) — every value reaching `Settings` inside Docker
arrives as a real process environment variable, already resolved by Compose.

5. DATABASE / MIGRATION CONSISTENCY RESULTS
================================================================================

A. Running server's database selection [TESTED via code reading,
   `build_sqlite_url()`/`create_database_engine()` in `persistence/
   database.py`]: always SQLite at `<settings.storage.data_dir>/kingsec.db`.
   No other source is ever consulted by the running server.

B. Alembic's migration database selection [TESTED via code reading,
   `_resolve_database_url()` in `kingsec/alembic/env.py`]: precedence is
   (1) `ALEMBIC_DATABASE_URL` env var, (2) `KINGSEC_STORAGE__DATABASE_URL`
   env var, (3) the same SQLite path the server would use, derived via
   `load_settings()`.

C. Docker Compose's database configuration: `docker-compose.yml` sets no
   database-related variable in its own `environment:` block at all — the
   database URL variables (if used) must come from the operator's own
   `.env` via `env_file:`.

D. `.env.example`'s description: BEFORE this phase (Phase 26's fix): stated
   `KINGSEC_STORAGE__DATABASE_URL` is migration-only and not honoured by the
   server. Confirmed still present and unmodified by Phase 27 in this file.
   README.md and docs/INSTALL.md, however, still described it as if it
   configured the running server generally — this phase's confirmed finding
   (Section 7, Finding 1).

E. Interpretation, reproduced live this phase [TESTED, Docker Scenario D,
   Section 6]: with a valid disposable `.env` (real JWT secret, pepper,
   encryption key) plus `KINGSEC_STORAGE__DATABASE_URL` set to a second,
   different SQLite path, `kingsec-migrate` ran all 30 migrations
   successfully against that second database, and the subsequent
   `python -m kingsec` step then failed immediately with `ConfigError:
   storage.database_url ... Extra inputs are not permitted`.

Answer to Step 3's central question — "can migrations target Database A
while the server connects to Database B without being explicitly warned?"
[TESTED]: Not quite as originally framed. The reproducible outcome is not
silent divergence (the server does not quietly connect to Database B) — it
is that the server refuses to start at all after migrations against
Database A succeed. This is still a genuine first-run trap (an operator
could reasonably believe they had configured both to use the same external
database and be confused why the server won't start after migrations
clearly worked), and it was undocumented anywhere outside `.env.example`
before this phase — README.md and docs/INSTALL.md both actively suggested
the opposite. Classified as a documentation defect, not a database-
architecture defect, and fixed accordingly (Section 9) — no code or
architecture change was made or is warranted; `Settings`'s own
`extra="forbid"` behavior is the correct, existing fail-closed guardrail
that makes this loud rather than silent.

7. FINDINGS
================================================================================

Finding 1 [TESTED, CONFIRMED — documentation defect, first-run/reliability
category, not security]: `README.md`'s "Database Migrations (Alembic)"
environment-variable table and `docs/INSTALL.md`'s "Environment Variables"
table (the latter explicitly claiming to be "verified against the running
application in this audit") both described `KINGSEC_STORAGE__DATABASE_URL`
as a general PostgreSQL/external-database override, with no indication that
it is migration-only and that setting it makes the running server refuse to
start. This is the same underlying defect Phase 26 already found and fixed
in `.env.example`, propagated to two further, more prominent locations (the
top-level README and the primary installation guide) that Phase 26 did not
audit. Reproduced live this phase (Section 6, Scenario D).

Finding 2 [TESTED, CONFIRMED — documentation defect, first-run category, not
security]: `.env.example`'s `KINGSEC_APP__ENVIRONMENT` comment gave no
indication that the provided `docker-compose.yml` (explicitly a production
deployment file, per its own header comment) hardcodes
`KINGSEC_APP__ENVIRONMENT=production` in its `environment:` block, which
always overrides whatever `.env` sets for the same key. An operator editing
`.env` to try `development` or `testing` via `docker compose up` would have
that choice silently ignored with no explanation anywhere in the documented
first-run workflow. Reproduced live this phase via `docker compose config`
(Section 4).

Finding 3 [TESTED, CONFIRMED — documentation staleness, not security]:
`docs/INSTALL.md`'s environment-variable table described
`KINGSEC_JWT__SECRET_KEY`/`KINGSEC_SECRETS__API_KEY_PEPPER` as "Required for
production" with the server "starts without it" outside production. This
was accurate before Phase 25/26's own fixes and is no longer accurate: both
are now rejected (placeholder and empty value) in every environment, not
just production. Left uncorrected, this table would actively mislead a
reader into believing non-production behavior is more permissive than it
now is.

No authentication, encryption, or database-architecture defect was found
this phase beyond what Phases 25/26 already identified and fixed. No new
code-level acceptance/rejection mismatch was found. All three findings are
documentation-only; per the phase's own instruction, none was inflated into
a security vulnerability, and no arbitrary new security policy was
introduced.

8. EXACT ROOT CAUSES
================================================================================

Findings 1 and 3 share a root cause: `.env.example`, `README.md`, and
`docs/INSTALL.md` are three independently-maintained descriptions of the
same configuration surface, with no single source of truth and no automated
cross-check between them. Phase 26 corrected `.env.example` in isolation
(its own explicitly stated scope) without auditing the other two documents
that describe the identical variables — a natural, narrow-scope gap in a
multi-file documentation set, not a code defect. [INFERRED, from the fact
that all three files described `KINGSEC_STORAGE__DATABASE_URL` identically
until Phase 26 changed only one of them, and from Phase 26's own final
report explicitly not mentioning README.md or docs/INSTALL.md.]

Finding 2's root cause: `docker-compose.yml`'s hardcoded
`KINGSEC_APP__ENVIRONMENT=production` is intentional, correct design (the
file is explicitly a production deployment artifact, confirmed by its own
header comment) — the root cause is purely that this consequence was never
surfaced to the operator at the one place they would naturally look
(`.env.example`'s own comment for that variable) before this phase.
[TESTED — confirmed via `docker compose config`, Section 4.]
