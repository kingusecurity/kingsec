DECISION 4 - nmap port scope
--------------------------------------------------------------------------
Your override (explicit port + host range, not port alone) required
determining the correct nmap invocation empirically, not guessing - a real
nmap 7.99 binary is installed on this machine, so it was tested directly
rather than inferred from documentation:

  nmap -p 18080,1-1000 --top-ports 50 ...   -> 50 services (--top-ports won)
  nmap --top-ports 50 -p 18080,1-1000 ...   -> 50 services (--top-ports won)
  nmap -p 18080 --top-ports 10 ...          -> 1 service  (-p won)

Combining -p and --top-ports as two SEPARATE flags does not reliably
resolve to "the last one wins" - which flag survives depends on the
CONTENT of the -p list (a range vs. only single ports), not command-line
position. This is not a documented, trustworthy contract to build a
"structural guarantee" on, so the design does not rely on it at all:

  nmap -p 18080,1-1000 ...   -> 1001 services (18080 + the 1-1000 range,
                                 combined WITHIN one -p list, not competing
                                 with a separate --top-ports flag) - VERIFIED

The fix: a URL-derived scan gets exactly one -p list combining the URL's
explicit port with NmapSettings.host_port_range (default "1-1000",
configurable). Requirement (d) - an operator-configured -p in scan_args
must not be able to silently drop the URL's port - is met by STRIPPING any
of -p/--top-ports/-p-/-F out of scan_args before appending our own -p,
rather than trying to out-position an unreliable flag (a warning is logged
naming exactly what was removed, so the override is visible, not silent).
Requirement (c) - the resolved spec recorded per run - is
ScannerResult.port_specification, populated by the SAME pure function
(resolve_port_specification()) _build_args() itself calls, so what's
recorded and what's scanned cannot drift apart.

Required test written and passing: a test asserting on the RECORDED SPEC
(ScannerResult.port_specification), not on flag presence, covering the
Phase 1 case by name (http://127.0.0.1:18080 -> "18080,1-1000") and an
operator-scan_args-collision case.

ADDITION 1 - IPv6, both paths
--------------------------------------------------------------------------
Verified against the real nmap binary: without -6, nmap treats a
bracket-stripped IPv6 literal as invalid and skips it outright -
"status=skipped reason=invalid", 0 hosts scanned, exit success. This is a
REAL, currently-reachable bug: any existing IP_ADDRESS target holding an
IPv6 value would silently produce zero findings today, indistinguishable
from a clean scan. Fixed for every target type, not just URL -
_resolve_host_and_ipv6() checks IP_ADDRESS via is_ipv6_literal(), NETWORK
via ipaddress.ip_network().version, URL via decompose_url()'s is_ipv6.
Required test (IPv6 IP_ADDRESS target) written and passing.

C2 - GRACEFUL HANDLING FOR A ROW THAT FAILS VALIDATION (proposed, NOT applied)
================================================================================

Traced every caller of assessment_to_domain() (mappers.py:287, which
constructs Target(orm.target_value, TargetType[orm.target_type]) - the
exact line that would start raising once Decision 3 lands):

  Single-fetch (2 call sites):
    - repositories/assessment.py: SQLAlchemyAssessmentRepository.get()
    - _operations.py: load_assessment()

  List-building (6 call sites, ALL a bare list comprehension today):
    - repositories/assessment.py: list(), find_by_schedule_occurrence_id(),
      find_running()
    - _operations.py: list_assessments(), find_running_assessments(),
      find_assessments_by_schedule_occurrence_id()

Every list site is exactly `[assessment_to_domain(o) for o in orms]` - one
bad row raises and the ENTIRE list call fails. This confirms the exact
risk you flagged, and it is worse than "a 500 on an unrelated HTTP
request": find_running_assessments() backs the STARTUP orphan-recovery
pass (ResolveOrphanedAssessments, Phase 2A FIX 9) - one corrupted row
there could fail application startup, not just one endpoint.

Also found, not previously documented: repositories/assessment.py and
_operations.py contain TWO INDEPENDENT implementations of the same three
queries (list/find_running/find_by_schedule_occurrence_id) - one using
SQLAlchemy 2.x select(), one using the older session.query() style. They
don't share code today, so any fix has to be applied in both places or it
silently only half-covers the risk. Flagging this now; not fixing the
duplication itself here - out of scope for this decision.

PROPOSED FIX (not implemented - shown for approval first, as instructed):

1. List-building call sites (all 6): wrap each row's
   assessment_to_domain(o) in a per-row try/except catching
   InvariantViolation and TargetDecompositionError. On catch: log the
   assessment's id ONLY - never target_value, which is exactly the class
   of value Decision 3 exists to stop exposing, so it must not leak
   through this error path instead - and skip that row; the rest of the
   list loads normally. find_running_assessments() specifically logs at
   ERROR, not WARNING: a RUNNING row the orphan-recovery pass can't even
   evaluate needs operator visibility, not a quiet skip that leaves it
   stuck RUNNING forever with no trace of why.

2. Single-fetch call sites (get()/load_assessment()): do NOT skip
   silently - the caller asked for this specific row, so silently
   returning nothing (or a confusing NotFound) would be dishonest.
   Propose a new, narrowly-scoped AssessmentDataCorruptedError
   (application/errors.py, sibling to AssessmentNotFoundError, not reusing
   it - "not found" and "found but unloadable" are different facts an
   operator needs to tell apart), mapped at the HTTP boundary to a clear,
   honest error response instead of a raw, opaque 500 traceback.

3. Not fixed here, flagged: the SQLAlchemyAssessmentRepository / _operations
   duplication above. Both need the same per-row handling since they don't
   share an implementation.

Files this would touch, not yet edited: mappers.py (or a new shared
helper), _operations.py, repositories/assessment.py, application/errors.py
(new error class). Four files, all shown above, none applied.
