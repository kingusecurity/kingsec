## 6. The Fernet cross-version decryption check

**Performed and PASSED**, in two parts:

**(a) Isolated key/ciphertext round-trip (the authoritative proof):** before touching `pyproject.toml` or the installed package, a value was encrypted via `FernetEncryptionService` under the then-installed `cryptography 49.0.0`:
```
cryptography version at capture time: 49.0.0
ciphertext: b'gAAAAABqhczziQzFHhWjJrFnVJEZ1BANFF8XrychYDDgyFe1VK...'
```
The key and ciphertext were saved to disk. After bumping to `cryptography 50.0.0`, the same ciphertext was decrypted with the same key:
```
cryptography version now: 50.0.0
DECRYPTION SUCCEEDED under cryptography 50.0.0
decrypted: phase11-cross-version-check-secret-value-12345
FRESH ROUND-TRIP under 50.0.0 also OK
AESBackupEncryptionService round-trip under 50.0.0 also OK
```
Both `FernetEncryptionService` (secrets-at-rest) and `AESBackupEncryptionService` (backup encryption) confirmed compatible.

**(b) Existing-persisted-volume check (a corroborating smoke test, with an honest limitation):** the freshly rebuilt `kingsec:2.0.0` image was started against `kingsec-data-phase09` — the volume Phase 09 deliberately left in place for exactly this purpose. The container reached `healthy` and `GET /api/v1/health` returned `{"status":"ok"}` with **zero** decrypt/Fernet/error log lines. However, direct inspection of the persisted SQLite database found **zero rows** in every table that could plausibly hold a Fernet-encrypted value (`ai_provider_config`: 0, `api_keys`: 0, `identity_providers`: 0) — Phase 09's own end-to-end proof never configured an AI provider or API key, only ran assessments. **This means the existing-volume check proves the application starts and operates normally against pre-existing data, but does not itself independently exercise a real persisted Fernet ciphertext** — that proof rests on check (a) above, which is authoritative and unambiguous. Stated plainly rather than implied: this is not UNKNOWN (a real check with a real result was performed), but its scope is narrower than "decryption of real persisted secrets was proven" — that specific claim rests on (a).

A second, older volume (`kingsec-data`) was also tried and found to hit Phase 09's already-documented Finding 5 (`Can't locate revision identified by 'fa44a8933db0'`) — confirmed still present, unrelated to this phase's changes, and left untouched per the explicit instruction not to fix Finding 5 here.
