================================================================================
5. EXACT FIX
================================================================================

Chosen mechanism (Dockerfile, Stage 1):

```dockerfile
FROM node:20-slim AS frontend-builder

WORKDIR /frontend

RUN apt-get update && apt-get install -y --no-install-recommends git && \
    rm -rf /var/lib/apt/lists/*

COPY .git ./.git
RUN git archive HEAD -- frontend | tar -x --strip-components=1 && rm -rf .git

RUN npm ci
RUN npm run build
```

This directly mirrors Stage 2's existing, already-proven backend mechanism
(`COPY .git ./.git` + `git archive HEAD | tar -x`), scoped specifically to
the `frontend/` subtree via `git archive`'s own pathspec support, with
`tar --strip-components=1` dropping the leading `frontend/` prefix so
extracted files land directly in the stage's `/frontend` WORKDIR — exactly
matching what the prior `COPY frontend/ ./` produced, content-wise, for
anything actually committed.

[TESTED, before modifying the Dockerfile] The exact extraction mechanics
were verified in an isolated local sandbox first: a copy of the real
`.git` directory was placed in a scratch directory, and `git archive HEAD
-- frontend | tar -x --strip-components=1` was run and inspected —
`package.json`, `index.html`, `vite.config.ts`, and all other `frontend/`
top-level entries appeared correctly at the extraction root, matching the
prior `COPY frontend/ ./` layout exactly.

Correctness rationale: `git archive`'s pathspec filtering (`-- frontend`)
operates on the tree object's own committed paths, independent of where
`.git` is physically copied to on disk — so placing `.git` inside
`/frontend/.git` does not cause git to misinterpret `frontend` as a
doubled/nested pathspec, confirmed by the sandbox test above producing
correct results.

Trade-off disclosed: the prior two-step `COPY package.json/lock` → `npm
ci` → `COPY rest of frontend/` → `npm run build` structure allowed Docker
to cache `npm ci` across commits that only changed `frontend/` source
files without touching `package.json`/`package-lock.json`. The new
single-archive-extraction step (`COPY .git` + `git archive`) invalidates
on every commit to the ENTIRE repository, not just `frontend/`-scoped
commits — because `.git`'s own content changes with every commit anywhere.
This is not a new class of problem: the backend `builder` stage already
has the exact same property (its own `COPY .git ./.git` step already
invalidates on every commit, accepted as a deliberate trade-off since Phase
15/16's original fix). This phase's frontend change makes that same,
already-accepted trade-off apply symmetrically to both stages, rather than
introducing a new one. `npm run build`'s own inherent non-caching (Vite
rebuilds fully each time regardless) means the actual wall-clock cost of
this trade-off is limited to `npm ci`'s dependency-install step.

================================================================================

- As in every phase from 25 through 29: no backend Python fix (here, the
  `health_routes.py` dead-code removal) can be observed inside an actual
  built Docker image without committing, since the backend `builder`
  stage's `git archive HEAD` step only ever includes committed content.
  This was verified directly and disclosed honestly (Section 9) rather

  (Section 13), and the dead code's presence or absence has zero effect on
  the externally observable `/api/v1/health` response either way, since it

- The frontend fix trades away a build-cache optimization (fine-grained

  matching the backend stage's own already-accepted trade-off (Section 5).
  This increases Docker build time modestly on repeated builds where only
