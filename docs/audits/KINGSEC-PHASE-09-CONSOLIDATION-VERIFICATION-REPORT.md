### Scenario 3 — An assessment that genuinely succeeds

**Setup required** (test scaffolding, disclosed in full, not a product fix): the shipped image bundles no scanner binaries at all (Section 4). To prove a genuine success path, the official Nuclei v3.11.1 release binary (`nuclei_3.11.1_linux_amd64.zip`, fetched from `github.com/projectdiscovery/nuclei`'s own releases, with the user's explicit permission for this specific action) was placed in the container's one writable, executable location (`/home/kingsec/.kingsec/`, the persisted data volume — `/tmp` is `noexec` per the compose file's own hardening). Nuclei's own template set was fetched via its standard `-update-templates` mechanism (also into the writable volume) — the first scan attempt against a target genuinely failed with `no templates provided for scan` before this step, which is what produced Scenario 2 above. The running container was given `KINGSEC_SCANNER__BINARY_PATH=/home/kingsec/.kingsec/nuclei` and `HOME=/home/kingsec/.kingsec` so both KingSec's own scanner adapter and Nuclei's own config/cache directories resolve inside the writable volume.

The first attempt used `target_type: "ip_address", target_value: "127.0.0.1"` — this was cancelled and redone as `target_type: "url", target_value: "http://127.0.0.1:8765"`, because a bare IP-address target causes Nuclei to probe the default HTTP/HTTPS ports (80/443), missing the app's actual port 8765 entirely. This correction is disclosed because it reflects a real usability gap: KingSec accepts an IP-address target type for a scanner that only produces useful results against a specific URL/port, with nothing in the request schema or API surface warning the caller.
