5. DOCKER BUILD REPRODUCIBILITY RESULTS
================================================================================

Methodology note: the Dockerfile's own builder stage requires a `.git`
directory to be present in the build context (`COPY .git ./.git`, then
`git archive HEAD` runs *inside* the build). A raw `git archive HEAD`
extraction (used for Section 3's completeness check) has no `.git` and
therefore cannot itself serve as a Docker build context. To faithfully
simulate "what another operator receives from Git" while still satisfying
the Dockerfile's actual mechanism, this phase used a fresh, **local-only**
`git clone` of the real repository at HEAD into a disposable directory
(`kingsec-phase29-clean`) — a clone can only ever contain committed history
plus a clean checkout with zero uncommitted changes, by construction, and
provides the `.git` directory the build genuinely needs. [TESTED —
`git rev-parse HEAD` inside the clone: `ab3a037...` (matches); `git status
--short` inside the clone: empty (zero uncommitted changes, as expected for
any fresh clone); `git remote -v`: points back to the local repository path
only, never any real remote — no network access occurred.]

  Command: `docker build -t kingsec:phase29-git-head .` (run from the
  clean clone's root)
  [TESTED] Exit code: 0. Build completed successfully in ~70s, including

  image assembly.
  Image ID: `ecedd5e2ab99` (distinct from `kingsec:2.0.0`'s `f0aa61a1597a`
  — confirmed via `docker images`, the pre-existing image was never

================================================================================
10. ROOT CAUSES
================================================================================

Finding 1 (Category J, fixed): root cause is that CI was designed around
"Standard Python OSS pattern" and "mirrors that shape for the Node side"
(the workflow file's own header comment) — the Docker deployment path was
never brought into that same quality-gate pattern when it was introduced,
and nothing since has required it to be.

Finding 2 (Category B, documented, not fixed): root cause is that the
Dockerfile's git-archive sanitization was added specifically to solve a
BACKEND problem (Phase 15/16's own documented history: "untracked Alembic
autogenerate artifacts... baked into every wheel"). The frontend build
stage was never subject to the same problem at the time and was never
retrofitted with the same protection when the backend fix was introduced,
leaving an asymmetry between the two build stages' actual guarantees
versus the Dockerfile's own single, unqualified comment describing "the
shipped artifact" as if the guarantee applied uniformly.

Finding 3 (Category G-adjacent dead code, documented, not fixed): root
cause is that FastAPI/Starlette does not raise an error, warning, or any
other signal when two different routers register a handler for the
identical path — the collision is entirely silent at both definition time
and registration time, and nothing in the test suite specifically asserts
on `health_routes.py`'s `health_simple()` being reachable (or its
non-reachability), so the shadowing has never surfaced as a test failure.

11. EXACT CHANGES MADE
================================================================================

Added one new job, `docker-build`, to `.github/workflows/ci.yml`:

```yaml
  docker-build:
    name: Docker Build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build image (no push, no run)
        run: docker build -t kingsec:ci-build .
```

Plus an explanatory header comment describing why the job exists (the
confirmed Category J gap) and explicitly noting it does not replace the
manual/disposable Compose verification this and prior phases perform.

The job only builds the image — it does not push to any registry, does not
run the container, and does not perform Compose-level deployment. This is
the smallest change that closes the specific, confirmed gap ("nothing in
CI ever builds the Docker image") without expanding CI's scope into
deployment testing, which remains a manual/audit-driven activity by
design.

Why larger alternatives are unnecessary: a full Compose-based CI
integration test (spinning up a database, generating secrets, running
migrations, hitting the health endpoint inside a GitHub Actions runner)
would meaningfully increase CI runtime and complexity for a benefit already
delivered, in this specific engagement, by this recurring series of manual
