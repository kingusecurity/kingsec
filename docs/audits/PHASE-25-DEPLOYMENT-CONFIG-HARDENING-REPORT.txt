3. EXACT ROOT CAUSE OF EACH CONFIRMED PROBLEM
================================================================================

Problem 1 (missing .env) and Problem 2 (.env.example placeholders → ConfigError)
are pre-existing, already-correct fail-closed behaviors, not defects. Their
root causes (`env_file: .env` referencing a possibly-absent file at the Compose
level; `Settings._guard_default_secrets_in_production()`'s production-only
placeholder/length checks at the application level) were re-confirmed by
direct code reading and are unchanged from Phase 23's original analysis.
[INFERRED from a fresh reading of docker-compose.yml and settings.py, TESTED
via the Docker reproductions in Section 2.]

Problem 3 (the real, confirmed root cause of the JWT gap):
`Settings._guard_default_secrets_in_production()` is the ONLY place in the
entire codebase that ever compared a JWT secret or API-key pepper against the
literal placeholder string, and it only runs its checks when
`self.app.environment is Environment.PRODUCTION`. No other validator, anywhere
in the composition root or provisioning layer, ever checked this before Phase
25. `Environment.DEVELOPMENT` is `AppSettings.environment`'s own default, so
any invocation that does not explicitly set `KINGSEC_APP__ENVIRONMENT=production`
— which specifically means any bare, non-Docker `python -m kingsec` run, since
Docker Compose hardcodes production unconditionally — was completely exempt.
[TESTED via direct code reading of settings.py, models.py, enums.py, and
empirically confirmed per Section 2, item 3.]

A second, related and previously undocumented gap was found and fixed as part
of the same root cause: `register_api_key_auth()` in
`infrastructure/auth/provisioning.py` also never validated
`settings.secrets.api_key_pepper` against the placeholder in any environment
— the API-key hasher could equally have been constructed from the same
publicly-known value. [TESTED — see Section 6, test
`test_placeholder_pepper_rejected_in_development`, which failed before the fix
and passes after.]

Important scope-clarifying finding: because Docker Compose hardcodes
`KINGSEC_APP__ENVIRONMENT=production` unconditionally (docker-compose.yml,
re-confirmed unchanged in this phase), the JWT-placeholder gap this phase
closes was NEVER reachable through `docker compose up` — Docker deployments
were always protected by the pre-existing production-only guard, both before
and after this fix. The gap was reachable only through a bare, non-containerized
`python -m kingsec` invocation left at its default (development) environment.
This is why none of the three Docker re-tests in Section 8 show any behavior
change: the fix's effect is invisible to Docker by construction, and correctly
so. [INFERRED from docker-compose.yml's hardcoded environment variable,
TESTED via the Section 2/8 Docker reproductions showing no behavior change.]

4. EXACT CHANGES MADE
================================================================================

(a) New shared constant, `DEFAULT_SECRET_PLACEHOLDER`
    (`src/kingsec/infrastructure/config/models.py`): the placeholder literal
    `"CHANGE-ME-IN-PRODUCTION-DO-NOT-USE-DEFAULT"` was previously duplicated
    across four independent locations (two field defaults in models.py, one
    local variable in settings.py's validator, one inline fallback in
    auth/provisioning.py). Consolidated into one named constant that all four
    now reference. This is a pure DRY change with no behavior change — the
    existing production-only guard in settings.py was updated to use the
    constant instead of its own local copy, and its behavior is provably
    identical (see Section 8, Docker scenario B, unaffected).

(b) New unconditional (all-environment) placeholder rejection at the
    composition root (`src/kingsec/infrastructure/auth/provisioning.py`):
      - `register_auth()` now raises `ConfigError` if
        `settings.jwt.secret_key` equals `DEFAULT_SECRET_PLACEHOLDER`,
        BEFORE constructing `JWTTokenService`. Runs in every environment,
        not just production.
      - `register_api_key_auth()` now raises `ConfigError` if `settings` is
        provided and `settings.secrets.api_key_pepper` equals
        `DEFAULT_SECRET_PLACEHOLDER`, BEFORE constructing `HmacApiKeyHasher`.
        Also runs in every environment. The existing `settings=None` fallback
        path (used by no current caller, confirmed by search) is left
        unchanged and unchecked, preserving the function's existing optional-
        settings contract.
    Both errors name only the offending environment variable and give a
    concrete generation command — never the secret value itself, matching the
    existing style of every other secret-related error in this codebase
    (`register_secrets()`'s encryption-key check, the production guard's own
    messages).

(c) `.env.example` documentation update: the JWT secret and API-key pepper
    comment blocks now state that a placeholder value is rejected in every
    environment (not just production), mirroring the phrasing already used
    for the encryption key's comment block. Pure documentation; no functional
    change.

(d) Test fixture updates (`tests/integration/bootstrap/test_composition.py`,
    `tests/integration/adapters/inbound/web/test_web_integration.py`): both
    files' `wired_app` fixture(s) — the only two places in the entire test
    suite that call `create_wired_application()` (confirmed by search) — now
    additionally `monkeypatch.setenv()` a real generated JWT secret and API-key
    pepper, extending the exact pattern already used there for the encryption
    key. Without this, both fixtures would now fail with the new ConfigError,
    since they previously relied on the (now-rejected) placeholder default.

Design rationale (why this location, not the `Settings` pydantic validator):
32 test files across the suite construct `Settings()` directly and rely on
development mode's previous leniency toward the placeholder (confirmed by
`grep -rln "Settings()\|JWTSettings()\|Settings(jwt=" tests/`). Extending the
existing `Settings`-level validator to reject the placeholder in every
environment would have broken all 32 of those files — inconsistent with
Objective 3's explicit instruction to implement a universal rejection "only if
it is compatible with the existing architecture and development workflow." The
composition-root location (`register_auth()`/`register_api_key_auth()`,
reached only via `create_wired_application()`) affects exactly 2 test files,
both already using the exact `monkeypatch.setenv()` idiom this fix extends.
This location also has a direct precedent already in the codebase:
`register_secrets()` already enforces its own unconditional (all-environment)
requirement for `KINGSEC_SECRETS__ENCRYPTION_KEY` at this same
composition-root layer, not inside `Settings`. The new checks are a sibling
of that existing, established pattern — not a new architectural layer.
[TESTED — the 32-file count and the exact 2 call sites were both confirmed by
direct search, not assumed.]
