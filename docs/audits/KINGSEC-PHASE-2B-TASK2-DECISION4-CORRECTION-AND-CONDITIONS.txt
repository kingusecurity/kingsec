PROPOSED FIX (adopting your suggestion, not arguing against it)
--------------------------------------------------------------------------
Your reasoning is correct and I'm not proposing an alternative: depending
on nmap's internal nmap-services file at runtime is fragile in a way that
matters here specifically - its exact install path varies by OS/package
manager, its content can change between nmap versions and package updates
without KingSec's own tests noticing, and (as Decision 4's original design
already established) it cannot be combined with an explicit -p as a
separate --top-ports flag at scan time anyway - the concrete port numbers
have to be materialized into KingSec's own -p list regardless of where
they come from. Given that, sourcing them from a runtime file read buys
nothing but fragility.

Proposed: capture a snapshot of nmap's real top-1000-by-frequency ranking
(the exact data just extracted above, from a real nmap install, not
invented) as KingSec's own explicit, documented, version-controlled
constant - e.g. infrastructure/scanner/nmap_default_ports.py, a tuple of
1000 ints with a docstring stating its provenance (nmap 7.99's
nmap-services, snapshotted <date>, frequency-ranked) and explicitly noting
it was chosen because it demonstrably covers every port Phase 1's Run #4
actually found. NmapSettings.host_port_range changes from a range string
to referencing this list; resolve_port_specification() unions it with the
URL's explicit port (deduplicating, same as today) and joins it into the
-p list nmap actually receives.

This is deterministic (frozen at commit time, not re-derived from whatever
nmap happens to be installed on a given machine), testable without nmap
installed at all (it's a plain Python tuple), and gives Task 4's
disclosure work an honest, inspectable spec to point to - "these are the
1000 ports KingSec checks by default" is a true, stable sentence once this
lands, which it is not today.

CONDITION 2 — ORPHAN RECOVERY MUST NOT SKIP SILENTLY
================================================================================

Read resolve_orphaned_assessments.py in full to check what it actually
needs. Its own docstring already states the scope precisely: "this never
touches a scanner, job runner, or the execution ledger" - and reading
execute()/_resolve_one(), it genuinely never touches target.value or
target.type either. It calls assessment.fail(reason) (a pure status
transition) and assessments.save(assessment) - the ONLY reason it needs a
full domain Assessment object at all is that find_running() currently
hands it one, fully reconstructed, Target included. The Target is
structurally irrelevant to what this use case does.

DECISION: resolve by ID without constructing a full Target - not "fail
startup loudly."

Reasoning: orphan recovery is best-effort, idempotent cleanup that runs
once at startup, before any new work is submitted (its own docstring).
Failing the entire application's startup because one orphaned row (out of
potentially many) has a corrupted Target is a disproportionate response -
it turns a narrow data-quality problem on one row into a total outage,
which is a worse failure mode than the one being fixed. The by-ID path is
also not a workaround bolted on for this one bug - it is a genuine
simplification of what this use case has always needed, since it never
legitimately required Target reconstruction in the first place.

PROPOSED FIX (not implemented):

  1. A new, narrow repository operation - NOT a variant of find_running()
     that still returns domain Assessment objects:

       AssessmentRepository.find_running_ids() -> tuple[str, ...]

     Backed by a query selecting ONLY the id column where
     status = 'RUNNING' - it can never fail on a corrupted target_value/
     target_type, because it never reads those columns at all.

  2. A second narrow operation for the actual transition:

       AssessmentRepository.force_fail_running(assessment_id: str,
                                                reason: str) -> bool

     A direct column UPDATE (status, failure_reason, updated_at) scoped to
     that one id AND status='RUNNING' (so it's a no-op, not a corruption
     risk, if the row already moved on for any reason) - again never
     touching target_value/target_type, never calling
     assessment_to_domain(). Returns whether a row was actually updated,
     so ResolveOrphanedAssessments can still know what it resolved for
     logging/audit purposes.

  3. ResolveOrphanedAssessments.execute() changes from "load full
     Assessment objects, call .fail() on each, save each" to:
     find_running_ids() -> for each id, force_fail_running(id, reason) ->
     publish an audit entry per id that was actually updated. This removes
     the Target-reconstruction dependency from the ENTIRE orphan-recovery
     path, not just the corrupted-row case - a structural fix, not a
     patch for one symptom.

REQUIRED TEST (specified, not yet written): insert an AssessmentORM row
directly at the ORM level (bypassing domain construction entirely, the
same way this round's C1 read data without going through the domain
layer) with status='RUNNING' and a target_type/target_value combination

Not yet implemented. Three files: the two new repository methods (port +
