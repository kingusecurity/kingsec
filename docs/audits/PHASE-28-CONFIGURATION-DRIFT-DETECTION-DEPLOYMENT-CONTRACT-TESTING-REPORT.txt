    → runtime effect: encrypts/decrypts stored secrets

  KINGSEC_APP__ENVIRONMENT
    → real Settings field (AppSettings.environment)
    → gates the production-only branch of the guard above
    → Compose-only behavior: docker-compose.yml's own `environment:` block
      hardcodes this to `production` unconditionally, which — confirmed
      empirically in Phase 27 via `docker compose config` — always wins
      over whatever `.env`/`env_file:` supplies for the same key. This is
      intentional (the shipped compose file is explicitly a production

  KINGSEC_STORAGE__DATABASE_URL
    → NOT a Settings field (confirmed by introspection: StorageSettings has
      only `data_dir`)
    → migration-only variable, read via raw `os.environ.get()` in
      `kingsec/alembic/env.py::_resolve_database_url()`
    → setting it makes the running server raise `ConfigError: ... Extra
      inputs are not permitted` (Settings' `extra="forbid"` on nested
      groups)
    → this is the one variable this phase's new guard explicitly allowlists
      as a deliberate, documented exception (Section 8).

  KINGSEC_STORAGE__DATA_DIR
    → real Settings field (StorageSettings.data_dir)
    → consumed by both the running server (`build_sqlite_url()`) and, as a
      fallback, Alembic migrations

  ALEMBIC_DATABASE_URL
    → NOT `KINGSEC_`-namespaced, deliberately outside the Settings contract
      by design (a plain Alembic/CI convention)
    → highest-precedence override in `_resolve_database_url()`
    → out of this phase's guard's scope by construction (the guard only
      inspects `KINGSEC_*` tokens), which is correct: it was never meant to
      be a Settings field and documenting it that way was never the defect.

================================================================================
7. ROOT CAUSE
================================================================================

Same root cause Phase 27 already identified: `.env.example`, `README.md`,
and `docs/INSTALL.md` are three independently-maintained, hand-written
descriptions of the same configuration surface, with nothing that
mechanically ties any of them back to the real `Settings` field set. Phase
28's specific finding is that this was never a solvable-by-vigilance problem
— it was a solvable-by-automation problem with no automation in place. The
gap is a missing test, not a missing runtime check: `Settings`' own
`extra="forbid"` behavior already correctly rejects an unrecognized field at
runtime (that mechanism was never broken); what was missing was anything
that checks the *documentation* against that same real field set *before* a
human notices the mismatch in production.

8. EXACT CHANGES MADE
================================================================================

Added `tests/unit/infrastructure/config/test_deployment_contract.py`
(Option A + a small, directly-coupled complement of Option B — see design
rationale below; Option C and D were considered and explicitly not
implemented, Section 6).

Contents:
  - `_real_settings_field_paths()`: introspects the live
    `Settings.model_fields` tree (same technique Phase 26/27 used ad hoc)
    to compute every `KINGSEC_<GROUP>__<FIELD>` path the code actually
    accepts — never a hand-maintained list.
  - `_documented_vars(text)`: extracts every `KINGSEC_[A-Z0-9_]+` token from
    a documentation file's raw text via a single, simple regex.
  - `_DOCUMENTED_NON_SETTINGS_VARS`: a one-entry, explicitly-commented
    allowlist (`KINGSEC_STORAGE__DATABASE_URL`) for the one variable that is
    deliberately documented but is not, and should not be, a `Settings`
    field.
  - `TestDetectionLogicCatchesTheHistoricalDefectShape` (3 tests): proves
    the detection function itself works, using synthetic input that
    reproduces the historical defect's exact shape, independent of the
    current (already-correct) state of any real file.
  - `TestDeploymentDocumentationMatchesRealSettingsFields` (1 parametrized
    test, 3 cases): the actual regression guard — runs the same detection
    logic against the real, current `.env.example`, `README.md`, and
    `docs/INSTALL.md`.
  - `TestMigrationOnlyVariablesRemainRejectedByTheRunningServer` (2 tests):
    pins the complementary direction of the same contract — that
    `KINGSEC_STORAGE__DATABASE_URL` is still actually rejected by `Settings`
    today (not just documented as rejected), and that the allowlist itself
    contains no now-stale entries (a name that has since become a real
    field would be flagged here, not silently pass).

Design rationale: Option A (documented-variable-is-a-real-field check) is
the direct, evidence-driven match for the exact defect that occurred twice
(Phase 26 in `.env.example`, Phase 27 found the same defect duplicated into
README.md and docs/INSTALL.md). The two small tests pinning the allowlist's
own correctness are a minimal, tightly-coupled complement addressing the
Primary Question's explicit reverse case ("a migration-only environment
variable is accidentally treated as a server setting") — not a separate
Option B implementation, but the other half of the same allowlist's
integrity. Option C (Compose-override contract test) and Option D (general
documentation-claim parsing) were both explicitly not implemented, per
Section 6's reasoning and Step 5's "do not automatically implement all
four" instruction. No `Settings` field, validator, provisioning function,
Docker file, or Alembic file was touched — this is purely a new, test-side
file, matching Step 5's "TEST THE CONTRACT... do NOT make runtime
application code responsible for documentation."

14. REMAINING LIMITATIONS
================================================================================

- The guard checks name correspondence, not documentation accuracy. It
  would not automatically catch a comment that misdescribes a real field's
  actual behavior (the exact kind of prose-level defect Phase 26/27 also
  fixed) — only that the name itself is either real or a deliberately
  allowlisted exception. Closing that gap would require prose/behavior
  parsing, which Step 5's Option D and this phase's own evidence-based
  minimalism explicitly caution against implementing without much stronger
  justification than exists today.

- Option C (an automated check that Docker Compose's production-forcing
  override "remains intentional and documented") was not implemented — no
  evidence surfaced this phase that this single hardcoded line is at
  meaningful risk of silent drift, unlike the three-file documentation
  duplication that already drifted twice. If a future phase's own
  evidence-driven investigation finds this assumption wrong, that would be
  the moment to add it — not preemptively here.

- The ~70 legitimate, currently-undocumented `Settings` fields (mostly
  `integrations.*`, `performance.*`) remain out of scope, exactly as Phase
  27 and this phase's own instructions specify — the new guard does not
  flag them, by design, since flagging "real field not yet documented" was
  never the demonstrated problem (the problem was the reverse: documented
  names that are not real fields).

- The full-suite pytest run's exact final numeric pass count could not be
  captured in this environment for the fourth consecutive phase (Section
  11) — a confirmed, reproducible environment limitation, unrelated to
  this or any prior phase's changes.

- Per this phase's own rules, Phase 24's secret-rotation design, Phase 25's
  composition-root placeholder guard, Phase 26's empty-secret/error-quality
  fixes, and Phase 27's documentation corrections were not touched and
  remain exactly as those phases left them (Section 3).
