## 5. 3.2 fix — the assertion repair, justified explicitly

The original assertion, `assert "No changes detected" in result.stderr or result.returncode == 0`, is a no-op: `alembic revision` returns 0 whether or not it writes a file, so the right-hand side is always true. It is now:
```python
tmp_files_after = set(tmp_versions_dir.glob("*.py"))
assert not tmp_files_after, (...)
real_versions_after = set(_REAL_VERSIONS_DIR.glob("*.py"))
assert real_versions_after == real_versions_before, (...)
```
Making "no file appeared" achievable at all (rather than the assertion being unsatisfiable, since Alembic writes a file — with empty `upgrade()`/`downgrade()` bodies — even on a genuinely empty diff) required a new hook in `env.py`, `_skip_empty_autogenerate_revision`, registered via `context.configure(..., process_revision_directives=...)`. This is Alembic's own documented recipe for suppressing empty-diff revisions; it fires only inside `revision --autogenerate` (checked via `ctx.config.cmd_opts.autogenerate`), never during `upgrade`/`downgrade`, so real migration application is unaffected. Verified directly against the real, unmodified `script_location` (not the test's isolated copy) before integrating it into the test:
```
INFO:alembic.env:no schema changes detected; skipping empty autogenerate revision
=== contents of tmp-only dir (expect empty, only __pycache__ maybe) ===
[empty]
```

**Justification per §0.4:** this is a repair, not a weakening. The assertion is *strictly stronger* than before (it can now fail; before it could not), and it immediately proved itself by catching a real, previously-undetectable defect — see §9's major discovery. An existing test's assertion changing shape, where the change makes a previously-unsatisfiable-as-written check meaningful without narrowing what counts as success, is exactly the "repair" the ground rules distinguish from "weakening."

## 6. 3.3 fix — options evaluated, reasoning for the one chosen

Evaluated all three options the prompt listed, empirically, not by inspection alone.

**Narrowing the `include` glob / explicit `exclude` for `*__no_changes.py` — REJECTED, proven unsafe:** `pyproject.toml`'s `include = [..., "src/kingsec/alembic/versions/*.py"]` is not, on inspection, the sole cause — Hatchling's `packages = ["src/kingsec"]` directive independently sweeps every `.py` file under the package tree regardless of `include`, confirmed by removing the explicit `include` entry entirely and rebuilding: the wheel still contained 71 files, 40 of them untracked. Adding an explicit `exclude = ["src/kingsec/alembic/versions/*__no_changes.py"]` **did** stop the untracked leakage (0 untracked in the resulting wheel) — but also **stripped 7 legitimately tracked migrations** that happen to share the exact same naming convention (committed in the project's own earlier history — see Phase 15 §3.2's mention of pre-audit "no changes" commits). Confirmed via `comm -13` diff against `git ls-files`: 7 tracked files missing from the wheel.

**`.gitignore`-based exclusion — REJECTED, same failure mode:** tested directly (`git check-ignore` confirmed the rule matched only the untracked files, correctly, since git itself never retroactively un-tracks a file). But Hatchling's own "VCS-aware" file selection (`hatchling/builders/config.py`'s `load_vcs_exclusion_patterns`) only *replays `.gitignore`'s patterns as additional filesystem excludes* — it does not query `git ls-files` for actual tracked status. Rebuilding with the `.gitignore` rule in place produced the identical result: 0 untracked, but the same 7 tracked files missing. **Both filename-pattern mechanisms are structurally incapable of solving this correctly for this repository**, because they can only match on name, and this repository's own legitimate history contains tracked files sharing the risky name.

**Enforcing a clean tree via true git-tracked status — CHOSEN, implemented as two independent, defence-in-depth layers, both verified empirically:**

1. **Dockerfile builder stage:** `COPY src/ ./src/` (plus the separate `COPY pyproject.toml README.md LICENSE ./`) replaced with `COPY .git ./.git` followed by `RUN git archive HEAD | tar -x && rm -rf .git`. Verified locally before touching the Dockerfile: `git archive HEAD | tar -x` into a scratch directory produced exactly 31 files in `versions/` (the 7 legitimately-named tracked ones included, 0 of the 40 untracked ones present). `.git` is added to the builder stage's `apt-get install` list only as `git` the binary; `.dockerignore` no longer excludes the `.git` directory itself (11 MB, confirmed via `du -sh .git` — a small, one-time context-transfer cost). `.git` is deleted within the same `RUN` layer and never reaches the runtime stage, which continues to `COPY --from=builder` only the built wheel.
2. **`hatch_build.py` (new custom Hatchling build hook):** protects the path the Dockerfile change does not cover — a bare `python -m build --wheel` run directly against a git checkout (which is exactly how Phase 15's Script 4 and this phase's own §8 wheel-determinism checks operate, independent of Docker). In `finalize()`, after Hatchling has already built the wheel normally, the hook runs `git ls-files src/kingsec/alembic/versions/` and strips any packaged `alembic/versions/*.py` entry whose basename isn't in that real, git-derived set — rewriting the zip in place. Deliberately fails open (no-ops) when `.git`/`git` is unavailable, which is safe specifically because the one place in this project that lacks `.git` at build time (the Docker builder stage, after its own `git archive` step deletes it) already has an independent, complete guarantee from mechanism 1.

**Why both layers, not one:** the prompt's own framing — "3.1 stops production, 3.3 ensures that even if something generates a stray file later, it cannot reach a shipped artifact" — and the fact that this project has two genuinely different build paths (Docker's multi-stage pipeline, and a bare `pip`/`build` invocation a developer or a non-Docker release process might use) that share `pyproject.toml` but not the Dockerfile. Protecting only one leaves the other exactly as vulnerable as before this phase.

## 7. 3.4 removal — verification method and count

Per §0.5, every file was verified untracked individually before deletion, using exactly the method specified: `git ls-files --error-unmatch <path>` per file (exit 123 = no match = untracked). Script:
```bash
while IFS= read -r f; do
  if git ls-files --error-unmatch "$f" >/dev/null 2>&1; then
    echo "TRACKED (should not delete): $f"; tracked_found=1
  fi
done < pollution_list.txt
```
Result: `VERIFIED: all files in the list are untracked (git ls-files --error-unmatch failed for every one)` — **40 of 40** files verified untracked, **0** found tracked (nothing stopped, per §0.5's contingency, because nothing needed to). All 40 were then deleted, along with a stray `versions/__pycache__` directory. **This produces no git commit** — deleting untracked files leaves no diff for git to record, since nothing was ever committed. ## 9. Major, unplanned discovery — a genuine pre-existing schema drift, surfaced by the fix working correctly

Re-running the full suite after §3.1–§3.4 produced **one failure**, not zero:
```
FAILED tests/integration/test_alembic_migrations.py::TestMigrationAutogenerate::test_autogenerate_on_clean_state_produces_no_changes
AssertionError: autogenerate against an up-to-date database wrote a new revision file:
['2026_08_21_123404__no_changes.py'] — this means the ORM metadata (models.py) and the
migration chain (versions/) have drifted and a real migration is needed.
```
Reproduced directly (not just via pytest) to inspect the generated content precisely. The autogenerate diff, against the real tracked head `d1e2f3a4b5c6`, is a batch of **index renames** across ten tables — `account_links`, `asset_history`, `asset_relationships`, `cve_entries`, `dead_letter_entries`, `exposures`, `identity_providers`, `job_leases`, `job_queue_entries`, `sso_sessions` (e.g. `ix_account_links_provider` → `ix_account_links_provider_id`). This is **not new** — it is byte-for-byte the same diff captured in the *very first* untracked pollution file this whole investigation traced, `2026_08_19_020109__no_changes.py`, read in Phase 15's own §2. **This drift has existed since at least 2026-08-19, silently, masked only by the no-op assertion this phase just repaired.** Neither `test_upgrade_creates_expected_indexes` (checks only `users`/`audit_entries`) nor `test_metadata_has_all_tables` (table names only) was positioned to catch it — the autogenerate test was the only one that could, and until this phase it could not fail regardless of what it found.

**This is not fixed in this phase.** Writing the missing migration is a schema change — outside the four things this phase's §3 scopes (stop generation, fix the assertion, make packaging deterministic, remove pollution). Per ground rule §0.7 ("if a fix requires exceeding this scope, stop and report that") and §0.4 (repairing a test's assertion is authorized; silently reintroducing a way for it to pass over a real problem is not), the test is marked:
```python
@pytest.mark.xfail(reason="...", strict=True)
```
with the full diff, its provenance, and the reason it's out of scope documented inline. `strict=True` deliberately: if a future phase writes the missing migration and this test starts passing, `strict=True` turns that into a hard failure (`XPASS`) rather than a silent, forgettable pass — forcing the marker's removal to be a deliberate act, not an oversight.

**Corrected full-suite result:** `errors="0" failures="0" skipped="1" tests="2882"` — junit reports `xfail` under `skipped`. That is **2,881 genuinely passing tests, 1 known-and-disclosed expected failure, 0 hard failures** — not the bare "2,882 passed" Phase 15's baseline reported, and this report states that difference plainly rather than rounding it away.
