## §2. §3.1 — Failure mode inventory (re-verified against current code, not copied from Phase 04)

Every `raise ScannerExecutionError(...)` in `src/kingsec/infrastructure/scanner/` was located directly (`grep -rn "raise ScannerExecutionError"`), plus every reachable `ScannerPluginError`/`ScannerUnavailableError` site feeding `engine.fail_scanner()`. Five distinct modes were confirmed — two more than Phase 04's original 3-mode summary (M4 and M5 were not named there):

| Mode | Raising site(s) | Exception type | Distinguishing detail at raise site | Distinguishable at `user_message` point? |
|---|---|---|---|---|
| **M1** binary absent | `runner.py:85-91` (`FileNotFoundError` translation, all 9 adapters share this runner call); **also** `application/ports/scanner_plugin.py:71-85`'s default `health_check()`, via each plugin's `is_available()` (all 9 plugin wrappers, identical pattern) | `ScannerExecutionError` (runner path) / `ScannerUnavailableError` (health-check path, a `ScannerPluginError` subclass — **not** a `KingSecError**) | The exception is raised directly on `FileNotFoundError`/`shutil.which()` miss — nothing else could produce it at that exact call | Yes — available and unambiguous at both raise sites |
| **M2** timeout | `runner.py:92-108` (`subprocess.TimeoutExpired` translation, shared by all 9 adapters) | `ScannerExecutionError` | Raised only on `subprocess.TimeoutExpired` | Yes |
| **M3** non-zero exit, no findings | 9x identical adapter guard clause: `nmap.py:58`, `nuclei.py:82`, `nikto.py:59`, `ffuf.py:59`, `gobuster.py:59`, `amass.py:58`, `trivy.py:59`, `zap.py:58`, `semgrep.py:58` | `ScannerExecutionError` | `result.returncode != 0 and not findings` — a shared, structurally identical condition across all 9 | Yes |
| **M4** templates directory missing (Nuclei only) | `nuclei.py:128` (`_validate_templates_dir`) | `ScannerExecutionError` | Fires only when `settings.templates_dir` is configured and `.is_dir()` is false, checked before any subprocess runs | Yes |
| **M5** required wordlist missing (ffuf, gobuster) | `ffuf.py:79`, `gobuster.py:79` (`_validate_config`) | `ScannerExecutionError` | Fires only when `settings.wordlist` is empty, checked before any subprocess runs | Yes |

**Critical question answered:** for all five modes, the distinguishing information is available directly at the existing raise site — none of it is lost by the time `user_message` would be set. This means **no new exception subclasses are needed**; a `user_message=` keyword argument at each existing raise site is sufficient, satisfying the "prefer the smaller change" instruction.

**Discovery made during this inventory, not in Phase 04's summary or Phase 07's own investigation:** M1's health-check path (`ScannerPluginPort.health_check()`'s default implementation, calling each plugin's `is_available()`) is a **second, independent code path** for the same failure mode. `orchestrator.execute()` calls `health_check()` before `scan()`, so for a genuinely-missing binary this path fires first in practice — `runner.py`'s own `FileNotFoundError` translation is the rarer, race-condition-only path (binary present at health-check time, removed before the subprocess actually runs). Because `ScannerUnavailableError` is a `ScannerPluginError`, `orchestrator.py` re-raises it **unwrapped** — Phase 07's `safe_failure_message()` sanitization never touches it. All 9 plugin wrappers' `is_available()` had the identical leaking pattern: `reason=None if found else f"<name> binary not found: {binary!r}"`. This is the same M1 failure mode, not a new one, and closing it is squarely in this phase's scope (see §5).

None of the five new messages (§4) start with `[XX-XX-000]` or `unexpected error in plugin '...':` — both patterns are anchored (`^`) and only strip *framing* that `orchestrator.py` itself adds, not message content. Confirmed by direct inspection and by the passing `TestBinaryAbsentAllThreeSurfaces`/`TestNonZeroExitAllThreeSurfaces` report-rendering assertions (§7), which exercise the real regex against the real message. `templates.py` required **zero changes** this phase.

All three surfaces trace back to the same sanitized value with no further collapsing in between:

- `GET /assessments/{id}` → `routes.py:503` → `ScannerSummaryView.skipped_reason` (`dto.py:361,371`) ← `submit_assessment.py:288` (`p.skipped_reason or p.error`) ← `engine.fail_scanner(..., safe_failure_message(exc))` (`orchestrator.py`, Phase 07).

- Scanner Coverage report section → `templates.py:656-660` (`_clean_scanner_reason(s.skipped_reason)`) ← same `skipped_reason` value as the first surface.

All three are fed by the identical single sanitized string — there is one place the fix needs to change the text, not three.

## §5. Fix implemented

**`src/kingsec/infrastructure/scanner/errors.py`** — added three shared, safe message constants with comments explaining why each is shared across multiple raise sites rather than duplicated:

```python
BINARY_ABSENT_USER_MESSAGE = (
    "The scanner binary could not be found. Check that this scanner is "
    "installed in the deployment environment."
)
NONZERO_EXIT_USER_MESSAGE = (
    "The scan process exited with an error before producing usable results. "
    "Check the scanner's configuration or try again."
)
WORDLIST_MISSING_USER_MESSAGE = (
    "The scanner's configured wordlist could not be found. "
    "Check the scanner's configuration in the deployment environment."
)
```

**`src/kingsec/infrastructure/scanner/runner.py`** — `FileNotFoundError` raise gained `user_message=BINARY_ABSENT_USER_MESSAGE`; `subprocess.TimeoutExpired` raise gained an inline `user_message=` that interpolates the configured timeout duration (judgement call, justified below).

**All 9 adapters** (`nmap.py`, `nuclei.py`, `nikto.py`, `ffuf.py`, `gobuster.py`, `amass.py`, `trivy.py`, `zap.py`, `semgrep.py`) — the shared non-zero-exit guard clause gained `user_message=NONZERO_EXIT_USER_MESSAGE`. `nuclei.py`'s templates-dir raise gained an inline M4 message. `ffuf.py`/`gobuster.py`'s wordlist raise gained `user_message=WORDLIST_MISSING_USER_MESSAGE`.

**All 9 plugin wrappers** (`plugins/{nmap,nuclei,nikto,ffuf,gobuster,amass,trivy,zap,semgrep}/adapter.py`) — `is_available()`'s `reason=None if found else f"<name> binary not found: {binary!r}"` changed to `reason=None if found else BINARY_ABSENT_USER_MESSAGE`. This closes the second M1 code path found in §2 — not a new failure mode, the same one, fixed at both its raise sites so a single constant is now the sole source of truth for M1's text.

Representative diff (`nmap.py`, identical shape across all 9):

```diff
-from .errors import ScannerExecutionError
+from .errors import NONZERO_EXIT_USER_MESSAGE, ScannerExecutionError
...
         if result.returncode != 0 and not findings:
             raise ScannerExecutionError(
                 f"nmap exited with code {result.returncode}",
                 context={
                     "returncode": result.returncode,
                     "stderr": result.stderr.strip()[:500],
                     "target": target.value,
                 },
+                user_message=NONZERO_EXIT_USER_MESSAGE,
             )
```

Representative plugin-wrapper diff (`nmap/adapter.py`, identical shape across all 9):

```diff
+from kingsec.infrastructure.scanner.errors import BINARY_ABSENT_USER_MESSAGE
...
         return PluginAvailability(
             available=found,
-            reason=None if found else f"nmap binary not found: {binary!r}",
+            reason=None if found else BINARY_ABSENT_USER_MESSAGE,
             required_dependencies=(binary,),
         )
```

**Explicitly not changed:** *when* a failure is raised, the guard clause's condition, or which exceptions map to which modes (Phase 04 §7's finding that touching guard-clause logic changes nothing customer-visible on its own still stands). The raw internal `message` string passed as the exception's first positional argument is unchanged in every raise site — it still reaches logs in full via the `__cause__` mechanism Phase 07 established, untouched by this phase (`test_orchestrator_error_logging.py`, a Phase 07 file, required zero changes and still passes).

**Judgement call — M2's interpolated timeout duration:** the configured timeout value is treated as product configuration, not infrastructure detail. Reasoning: it's an admin-set number of seconds visible in the scanner's own settings, not a path, hostname, or credential; it's the one piece of information that makes the message actionable ("raise it if this target is legitimately slow"); and unlike a binary path or stderr excerpt it carries no information about the deployment's filesystem layout or network topology. This is the one deliberate exception to §2's "never interpolate" rule, made explicitly rather than by default.
