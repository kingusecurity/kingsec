1. TWO-INVOCATION NMAP DESIGN - IMPLEMENTATION
--------------------------------------------------------------------------------

Requirement 1 - non-URL targets unchanged:
  IP_ADDRESS/HOSTNAME/NETWORK targets get exactly one nmap invocation, no
  port flag at all - byte-identical to before this feature existed.
  Regression test added: TestNonUrlTargetsNeverGetAPortFlag
  (test_nmap_plugin.py), parametrized over all three target types, fails
  if -p/--top-ports/-p-/-F is ever introduced for any of them.

Requirement 2 - URL targets, two invocations, merge+dedupe:
  (a) host sweep - no port flag at all, nmap's own real default.
  (b) explicit port - "-p <port>" only, never combined with a range or
      --top-ports in the same invocation (the one case verified safe
      against a real nmap 7.99 binary - see the port-scope-measurement
      report for the empirical flag-conflict testing).
  Results merged and deduplicated by (port, protocol), extracted from
  each Finding's "Open port N/proto" title via regex. Tests:
  TestUrlTwoInvocationMerge - two invocations issued, sweep has no -p,
  explicit invocation has only the URL's port, a duplicate open port from
  both invocations collapses to one Finding, distinct ports from each
  invocation both survive.

  BUG FOUND WHILE WRITING THESE TESTS, FIXED: the "sweep" invocation only
  stripped an operator-configured -p from scan_args when port_spec was
  not None - but the sweep call always passes port_spec=None, so an
  operator's own -p in scan_args would silently survive into the sweep,
  making it scan the operator's configured port instead of an actual
  unconstrained default. Fixed in _build_single_invocation_args(): port
  selector flags are now stripped for BOTH of a URL target's invocations
  (keyed off target.type is TargetType.URL), never for non-URL targets
  (which must stay byte-identical, operator -p included).

Requirement 3 - failure semantics:
  Both invocations succeed -> clean success, no warning.
  Both fail -> ScannerExecutionError, scan reaches FAILED.
  Exactly one fails -> SUCCEEDED with a warning naming which sweep
  failed, via the new ScannerRunSummary.warnings plumbing (your stated
  preference - "SUCCEEDED with partial results and no disclosure" was
  rejected, not adopted).
  Tests: TestUrlTwoInvocationFailureSemantics - both-succeed-no-warning,
  both-fail-raises, sweep-fails-explicit-succeeds-warns,
  explicit-fails-sweep-succeeds-warns. A test-local _BranchingRunner
  double was needed (the shared FakeRunner returns the same canned result
  for every call; this one branches on whether -p appears in the args to
  tell the two invocations apart).

Requirement 4 - honest port_specification:
  Now reads "nmap's own default port sweep + explicit port <N>" - never
  a literal port list KingSec cannot verify. TestPortSpecification was
  rewritten (its old assertions expected a comma-joined port list from
  the now-abandoned 61-port-default design and would have silently
  passed against the wrong invariant otherwise).

Requirement 5 - the 61-port list's docstring:
  nmap_default_ports.py's module docstring now states plainly that
  nothing in the live scan path references DEFAULT_PORTS or
  DEFAULT_PORTS_SPEC - it is a documented, licensing-clean floor for a
  future scenario (nmap's own default data unavailable/disabled), not a
  default. The data itself is unchanged.

Requirement 6 - timing (measured BEFORE this report, as required):
  Real nmap 7.99 binary, target 127.0.0.1:
    Sweep invocation (no -p, nmap's own default):        13.284s
    Explicit invocation (-p 18080 only):                  0.555s
    Combined, sequential (as the real code path runs it): 12.704s
  The sweep dominates total time almost completely - the explicit
  invocation adds roughly 4% on top of it. This is NOT simply "double"
  the pre-existing single-invocation time; it depends entirely on what a
  URL target's ONE invocation looked like before this feature existed.
  On this host, expect a URL-target nmap scan to take on the order of
  nmap's own default sweep time, plus a small fixed overhead - worth
  knowing before Task 6's E2E run, since it is the single largest latency
  contributor in a URL-target assessment.

3. DECISION 3 - TARGET VALIDATION TIGHTENING
--------------------------------------------------------------------------------

Moved the credential/port-range/unbracketed-IPv6 checks from
decompose_url() up into Target._validate_format()'s URL branch. A
Target can no longer be constructed with embedded credentials, a
non-numeric or out-of-range port, or an unbracketed IPv6-shaped
authority - InvariantViolation now, at construction, not
TargetDecompositionError later, at decompose_url() time.

Probed the "unbracketed IPv6" case directly against Python's
urllib.parse before implementing: an unbracketed IPv6 authority
("http://::1/") already surfaces as a ValueError from parsed.port (the
extra colons make the port ambiguous) - no separate check was needed,
it falls out of the same port-parsing path as a non-numeric port.

ANSWER TO "can decompose_url() still raise for a constructed Target?":
  Yes, but only for ONE reason now, not four. Calling decompose_url() on
  a Target whose type isn't URL at all still raises
  TargetDecompositionError - that's a caller-contract violation
  Target._validate_format() has no way to prevent (it only runs for
  TargetType.URL values). The other four rejection branches inside
  decompose_url() (credentials, non-numeric port, out-of-range port, no
  usable host) are now provably unreachable for any Target actually
  reachable in this codebase: every construction site
  (infrastructure/persistence/mappers.py, the only place URL Targets are
  reconstructed from persisted data) uses the normal Target(value, type)
  constructor, which always runs __post_init__ -> _validate_format()
  first. They are kept in decompose_url() anyway, as cheap
  defense-in-depth against a future bypass, not deleted - deleting them
  would make decompose_url() silently trust a precondition it cannot
  itself verify.

6 tests in test_target_decomposition.py that previously called
decompose_url() to trigger these rejections now fail at Target()
construction instead - moved to a new TestTargetUrlConstructionRejects
class, asserting InvariantViolation directly. Verified via C1 (this
session's earlier read-only query against both databases): the one
distinct URL target_value in either database
("http://127.0.0.1:18080") passes all four tightened checks cleanly -
zero existing rows would be rejected retroactively.
