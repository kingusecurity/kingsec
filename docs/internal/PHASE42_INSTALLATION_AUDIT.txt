KingSec v2.0.0 — Phase 42: Final Release Engineering / Installation Audit
============================================================================

Scope: validate that a brand-new user can install and run KingSec from
scratch on a clean Windows machine, using only what README.md, INSTALL.md,
and QUICK_START.md tell them to do. No redesign, no refactor, no
optimization, no new features. Runtime code was touched only where a
genuine installation bug was found (none were — see below); everything
else was a documentation defect.

Every claim below was verified by actually doing it: a real wheel build,
a real fresh venv, a real pip install, real migrations against an empty
database, a real server start/stop/restart, real HTTP calls (register,
login, create/start/complete an assessment against 127.0.0.1 with a real
Nmap scan, generate a report), and a real `npm run dev`.

2. INSTALLATION ISSUES FOUND
============================================================================

A. CRITICAL (documentation) — The documented "quick start" cannot reach
   the web UI at all.
   Verified: `GET /` on the backend returns `404 Not Found`. There is no
   `StaticFiles` mount or any other frontend-serving code anywhere in
   `src/kingsec/`, and the `Dockerfile` never copies or builds `frontend/`.
   The frontend is a fully separate Vite/React app
   (`frontend/vite.config.ts` hardcodes a dev-proxy target of
   `http://127.0.0.1:8765`; `frontend/README.md` already documents this
   correctly, but nothing in README.md, INSTALL.md, or QUICK_START.md said
   so). All three top-level docs told a new user to `docker run ... -p
   8765:8765` and then "open http://127.0.0.1:8765" expecting a login
   page — they would get a bare JSON 404 instead.
   Disposition: documentation bug, not a code bug — building a
   backend-served-frontend capability would be a new feature, out of
   scope this round. Fixed by rewriting all three docs to state plainly
   that the frontend must be run separately (`cd frontend && npm install
   && npm run dev`, open `http://localhost:5173`), and by pointing the
   "quick start" URL at `/docs` (Swagger UI) instead.

B. CRITICAL (documentation) — The very first command in README.md's
   Quick Start would crash the container on startup.
   Verified: `KINGSEC_SECRETS__ENCRYPTION_KEY` is unconditionally required
   (`src/kingsec/infrastructure/secrets/provisioning.py:16-22`,
   `src/kingsec/infrastructure/config/models.py:524` — the field itself
   is commented "REQUIRED ... Startup fails if absent"). The README's
   top-of-file `docker run` example passed no `--env-file` and no `-e`
   flags at all, so a copy-pasted first command would produce a
   `ConfigError` and an immediately-exited container.
   Fixed: the Quick Start example now generates and passes the key
   inline; the fuller Installation section instructs editing `.env`
   before `docker run --env-file .env`.

C. HIGH (documentation, contradicts actual behavior) —
   `.env.example`'s comment on `KINGSEC_SECRETS__ENCRYPTION_KEY` said "If
   left empty, secrets encryption is disabled (local dev only)." Verified
   live: leaving it unset does not disable anything — the server raises
   `ConfigError` and refuses to start, in every environment, no
   exceptions. Fixed the comment and added a real example generated key
   (matching how the two sibling required secrets are already presented
   in the same file).

D. HIGH (documentation, entirely fictional) — INSTALL.md and
   QUICK_START.md were written for a different, unreleased version and
   described capabilities that do not exist in this codebase:
   - Both were titled "v1.1.0" (actual: 2.0.0, per `pyproject.toml`).
   - Both referenced pulling a published Docker Hub image
     (`kingusecurity/kingsec:1.1.0`) — no such image is published; the
     real `docker-compose.yml`/`Dockerfile` build locally.
   - Both used `pip install kingsec==1.1.0` / `pip install kingsec` — no
     PyPI package is published; the real path is `pip install .` from a
     git checkout.
   - Both invented CLI subcommands that do not exist: `kingsec db
     init/migrate/rollback/backup/restore/check`, `kingsec start --host
     --port`. The real CLI (`pyproject.toml`'s `[project.scripts]`) has
     exactly three entry points: `kingsec`, `kingsec-migrate`,
     `kingsec-bootstrap` — verified by installing a real wheel into a
     fresh venv and listing the generated scripts.
   - Both used wrong env var names (`KINGSEC_SECRET_KEY`,
     `KINGSEC_JWT_SECRET`, `KINGSEC_JWT_ALGORITHM`,
     `KINGSEC_JWT_EXPIRY_MINUTES`) — the real convention throughout the
     entire codebase is double-underscore
     (`KINGSEC_JWT__SECRET_KEY`, etc.), confirmed against
     `.env.example` and every settings model.
   - Both used wrong health/version endpoints
     (`GET /api/health` → `{"status":"healthy","version":...,"uptime":...}`,
     `GET /api/version`) — verified the real endpoint is
     `GET /api/v1/health` → `{"status":"ok"}` only, and no `/api/version`
     endpoint exists anywhere in the codebase.
   - Both used wrong container paths (`/app/data`, `/app/logs`,
     `/app/reports`) — the real `Dockerfile` uses
     `/home/kingsec/.kingsec` as the single data directory; there is no
     logs or reports subdirectory.
   Fixed: both files rewritten from scratch against verified, real
   behavior.

E. HIGH (confirmed real installation gap, Windows) — PDF report
   generation fails on a fresh direct (non-Docker) install.
   Verified end-to-end: fresh venv → wheel install → migrate → start →
   register → login → create/start/complete a real assessment against
   127.0.0.1 (7 real findings from Nmap) → generate report →
   `500 {"error_code":"KS-REPORT-001","message":"The report could not be
   generated."}`, with the server log showing "WeasyPrint could not
   import some external libraries." WeasyPrint needs system-level
   GTK/Pango/Cairo libraries that `pip install` does not provide on
   Windows. This was previously covered by one vague line in
   TROUBLESHOOTING.md ("verify WeasyPrint dependencies are installed")
   with no actionable instructions.
   Disposition: not a KingSec code bug — WeasyPrint's own documented
   platform requirement. The Docker image already bundles the needed
   libraries and is unaffected. Fixed by adding real, OS-specific fix
   instructions to TROUBLESHOOTING.md, INSTALL.md, and QUICK_START.md.

F. MEDIUM (documentation, fictional) — `frontend/README.md` documented
   an "Environment Variables" section (`VITE_API_BASE_URL`,
   `VITE_BACKEND_URL`) as build-time-configurable. Verified: neither
   variable is referenced anywhere in the frontend source —
   `src/api/client.ts:1` hardcodes `API_BASE = '/api/v1'` and
   `vite.config.ts` hardcodes the dev-proxy target. Changing either
   documented variable would have zero effect. Fixed by replacing the
   section with the accurate statement (both are hardcoded in source;
   editing them requires editing the file, not an env var).

G. LOW (documentation, stale) — `frontend/README.md` said "Version 1.0.0
   — Release Candidate 1 (RC1)" and listed `VITE_BACKEND_URL`'s default
   as `http://127.0.0.1:8000` (real default target is `8765`). Fixed.

H. LOW (documentation, wrong password policy) — Both original
   QUICK_START.md and my own first draft of the rewrite stated a
   password policy of "minimum 12 characters ... and special character."
   Verified against the actual validation code
   (`src/kingsec/application/use_cases/register_user.py:112-123`): the
   real policy is 8–128 characters with an uppercase letter, a lowercase
   letter, and a digit — no special character is required. Caught and
   corrected before finalizing, specifically because this pass verifies
   every claim rather than trusting the previous (also wrong) document.

I. LOW (environment, not a bug) — `pyproject.toml` declares
   `requires-python = ">=3.11"` and classifiers only through 3.13. This
   entire audit was run on Python 3.14, and everything worked — a wheel
   built, installed, migrated, and ran a full assessment/report cycle
   without issue. Not changed (classifiers are a forward-looking support
   declaration, not a functional bug, and "add 3.14 as declared-supported"
   is a judgment call belonging to the maintainer, not something to
   silently assert in a docs-audit pass) — instead documented as an
   observation in INSTALL.md's requirements table.

J. LOW (environment quirk, not a bug) — In this development environment,
   `pip show kingsec` reported version `1.0.0` while `pyproject.toml`
   says `2.0.0`. Root-caused: this machine has an editable install
   (`pip install -e .`) whose cached `.dist-info` metadata was generated
   before the version was bumped and never regenerated. Verified this is
   purely a `pip`/editable-install caching quirk, not a real defect: a
   genuine non-editable wheel build + install in a brand-new venv
   correctly reported `2.0.0`, and the running application's own
   self-reported version (`src/kingsec/__init__.py:3`,
   hardcoded `__version__ = "2.0.0"`, never read from package metadata)
   was correct throughout this entire engagement regardless of what `pip
   show` said. Documented as a one-line troubleshooting note (re-run
   `pip install -e .` after pulling updates) rather than treated as a bug.

============================================================================
5. FINAL INSTALLATION GUIDE (condensed — see INSTALL.md/QUICK_START.md
   for the full, rewritten versions)
============================================================================
Docker (fastest path to a running API):
  1. docker build -t kingsec:2.0.0 .
  2. Generate a key: python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
  3. docker run -d --name kingsec -p 127.0.0.1:8765:8765 \
       -e KINGSEC_SECRETS__ENCRYPTION_KEY="<key>" \
       -v kingsec-data:/home/kingsec/.kingsec kingsec:2.0.0
  4. curl http://127.0.0.1:8765/api/v1/health  →  {"status":"ok"}
  5. Swagger UI: http://127.0.0.1:8765/docs

Browser UI (separate, always required for a web interface):
  1. cd frontend && npm install && npm run dev
  2. Open http://localhost:5173 (proxies to the backend above)

Direct / non-Docker:
  1. git clone ... && cd kingsec
  2. python -m venv .venv && activate it
  3. pip install .
  4. export KINGSEC_SECRETS__ENCRYPTION_KEY="<generated key>"
  5. kingsec-migrate
  6. kingsec
  Windows-only: if PDF report generation 500s with KS-REPORT-001, install
  the GTK3 runtime (see TROUBLESHOOTING.md) — Docker installs are
  unaffected.

First run: register the first account via POST /api/v1/auth/register (or
the UI's Register screen) — it is automatically granted Admin. Log in,
create an assessment, start it, poll until completed, generate and
download a report. All of the above was executed for real during this
audit and works exactly as described.

============================================================================
6. PRODUCTION READINESS ASSESSMENT
============================================================================
The backend installation and runtime path (build/install → migrate →
start → register → login → run a real assessment → generate a report →
restart → data persists) is genuinely production-capable and was
verified end-to-end with zero code changes required. The frontend build
and dev-server path is also genuinely solid (clean `npm install`,
`npm run dev`, `npm run build`, `npm test` — all previously verified in
earlier phases of this audit).

The gap is entirely in how the product is presented to a new user:
before this pass, README.md/INSTALL.md/QUICK_START.md described a
different, apparently-earlier-planned v1.1.0 packaging story (a published
Docker Hub image, a richer CLI, a single-container web UI) that was never
built, alongside wrong env vars and wrong endpoints that would have
stopped a new user at the very first command. None of that reflects a
defect in the shipped v2.0.0 code — it reflects documentation that was
never updated to match what actually shipped. That gap is now closed:
every instruction in the rewritten docs was executed for real against
the actual codebase during this audit, not assumed.

KingSec v2.0.0's actual installation and first-run path is
production-ready as documented in the rewritten INSTALL.md and
QUICK_START.md, with two remaining caveats that are now accurately
disclosed rather than hidden: (1) there is no bundled production hosting
path for the browser UI — operators must serve `frontend/dist/`
themselves behind a reverse proxy; and (2) PDF report generation on
non-Docker installs requires a manual, one-time native-library install on
the host OS.
