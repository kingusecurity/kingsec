KingSec — Phase 49: Production Release Audit (Final Engineering Review)
==========================================================================

==========================================================================
EXECUTIVE SUMMARY
==========================================================================

Overall production readiness score: 87/100

KingSec's core product works end-to-end — verified this session by
actually running it: installed into an isolated environment, registered
the first user (auto-promoted to admin), created an assessment, started
a real Nmap scan against a live target, watched it complete in ~16
seconds, reviewed the 7 real findings it produced, and exercised report
generation, the Findings/Reports pages, and AI Copilot. All 26
navigation pages render without console or network errors. The backend
test suite passes except two long-standing, unrelated, already-
documented failures; the frontend suite passes 265/265 with a clean
tsc -b and production build.

The engineering foundation is solid: hexagonal architecture boundaries
are enforced by import-linter, dead code is sparse for a codebase this
size, and prior audit passes already removed a proprietary-license-
violating PyPI auto-publish step, a drifted dependency declaration that
broke the documented dev-setup path, and a dead Docker build step. This
session additionally found and fixed a Critical defect (the "Start"
button on a freshly created assessment never appeared, blocking the
single most important workflow in the product) and a High-severity
defect (rate-limit responses on login could report contradictory
"remaining requests" alongside a 429 rejection).

What remains is a short list of real, verified issues below Critical
severity — a dead-end external repository URL referenced in 18 files
(including the vulnerability-disclosure link in SECURITY.md), a
browser-session-persistence gap that logs a user out on any page
refresh or deep link, and a handful of cosmetic/packaging cleanup
items.

GO / NO-GO recommendation: GO, conditional on the High-priority items
below being addressed in the immediate next patch — not blocking a
controlled/initial release, but customer-visible enough to fix quickly.

HIGH PRIORITY ISSUES (Should be fixed before release)
==========================================================================

1. Dead-end repository URL referenced in 18 tracked files
   Evidence: https://github.com/kingusecurity/kingsec returns a live
   HTTP 404 (re-verified via direct fetch this session). It's the value
   of Homepage/Documentation/Source/Issues/Changelog in
   pyproject.toml:75-79, the vulnerability-disclosure link in
   SECURITY.md, and the clone instructions in README.md,
   docs/INSTALL.md, docs/QUICK_START.md, docs/USER_GUIDE.md,
   docs/ADMIN_GUIDE.md, docs/SCANNER_GUIDE.md, CONTRIBUTING.md,
   docs/internal/PRODUCTION_RELEASE_CHECKLIST.md, and 8 files under
   docs/commercial/. Not fixable without a real destination — requires
   either standing up the repository there or supplying the correct
   URL.

2. Browser session is destroyed by a page refresh or a deep link
   Evidence: frontend/src/api/client.ts:3-4 — accessToken/refreshToken
   are plain module-level JavaScript variables with zero persistence
   (confirmed via repo-wide grep: no localStorage/sessionStorage/cookie
   usage anywhere in the auth path — frontend/src/store/auth.ts is a
   bare Zustand store with no persist() middleware). Confirmed live,
   three separate ways this session: a hard reload, and navigating
   directly to a bookmarked/shared assessment URL, both immediately
   bounce an authenticated user to /login — even though the refresh
   token is still valid server-side (the backend sets no session cookie
   at all — confirmed via repo-wide grep of the web adapter layer). No
   data is lost (scans keep running server-side), but this hits every
   customer on the most ordinary browser action.

3. Two independent, uncoordinated rate limiters govern /auth/login, and
   the configurable one doesn't actually bind
   Evidence: src/kingsec/infrastructure/middleware/rate_limit.py
   enforces a token bucket sized from
   KINGSEC_RATE_LIMIT__AUTH_REQUESTS_PER_MINUTE (default 20/min), while
   src/kingsec/adapters/inbound/web/rate_limit_deps.py:25 hardcodes a
   second, stricter, non-configurable limit
   (RateLimitGroup.LOGIN: (5, 900, IP_USER) — 5 requests per 15 minutes)
   that actually governs login throttling; the config setting has no
   effect on it. The header-inconsistency symptom this produced (a 429
   simultaneously claiming 19 of 20 requests "remaining") was fixed this
   session (commit ac0dbe5); the underlying dual-system design was
   deliberately left as a flagged decision, not a code fix, since
   resolving it means choosing which system is authoritative.

MEDIUM PRIORITY ISSUES (Cleanup recommended)
==========================================================================

- assets/logo/, assets/icon/, assets/images/, docs/screenshots/ are all
  empty (untracked, not part of the actual git repo).
  docs/commercial/screenshot-checklist.md already lists exactly what's
  needed, but it was never executed.
- release_manifest.json contains "git": {"commit": "HEAD", "branch":
  "main", "dirty": false} — "HEAD" is the literal string, not a
  resolved commit hash, and the hand-maintained counts
  (endpoints_count, tables_count, python_total, etc.) will silently go
  stale with every future change. Reads as fabricated metadata to a
  technical reviewer.
- Five frontend components have real unit-test coverage but are never
  imported by any page:
  frontend/src/components/features/findings/{FindingCard,
  FindingFilters,FindingsTable}.tsx,
  frontend/src/components/features/monitoring/NotificationBadge.tsx,
  frontend/src/components/shared/LoadingOverlay.tsx (verified via grep
  — zero importers outside their own dedicated test files). Not
  deleted, since removing them would mean deleting real test coverage;
  a product decision on whether to wire them in or retire them (and
  their tests) is still open.
- src/kingsec/infrastructure/persistence/repositories/
  _legacy_repositories.py's SqlAlchemyAssessmentRepository/
  SqlAlchemyReportRepository and repositories/assessment.py's
  SQLAlchemyAssessmentRepository are both live, both wired
  (infrastructure/persistence/provisioning.py:79-80), differing only in
  the capitalization of "Sql"/"SQL" — a readability hazard, not a
  functional bug.
- Three frontend pages (ExecutionHistoryPage.tsx, KevViewPage.tsx,
  CveExplorerPage.tsx) hand-roll their own pagination instead of
  reusing the existing shared components/ui/Pagination.tsx.
- Six untracked *__no_changes.py alembic migration stub files recur
  every time a source file is edited in this dev environment (a
  background-hook artifact, not a code defect);
  docs/architecture/alembic_notes.md already documents this pattern for
  the ones that ARE tracked and correctly recommends against squashing
  them preemptively.

SECURITY AUDIT
==========================================================================

debug: bool = False is the default
(src/kingsec/infrastructure/config/models.py:64). No hardcoded or
sample credentials exist anywhere in src/kingsec (confirmed via grep).
Server binds to 127.0.0.1 by default per README/.env.example, with an
explicit opt-in flag required to bind externally. Error handlers return
domain-crafted messages (str(exc) on already-sanitized application
exceptions) or a fixed generic message for unhandled exceptions — no
raw Python tracebacks are exposed to the client anywhere in
error_handlers.py. Secrets are typed SecretStr and masked in
logs/repr. .env.example ships fully-formed example secret values
(commented out, with explicit "GENERATE A NEW RANDOM SECRET"
instructions) rather than an obvious placeholder token — a minor risk
that someone copies the example verbatim, mitigated by the surrounding
warning text. The rate-limiting/lockout gap covered under High Priority
is the one substantive security-adjacent finding from this pass; no
other security regressions were found.

listed (a dead repo link, and no in-app warning that a page refresh
will sign you out).
