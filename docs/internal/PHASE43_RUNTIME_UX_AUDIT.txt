KingSec — Phase 43: Production Readiness Audit & Runtime UX Alignment
==========================================================================

## Executive Summary

Traced all five pre-reported symptoms to root cause and fixed every
genuine, verified defect found: a Viewer could complete the entire
assessment-creation wizard before hitting a raw 403 (frontend never
checked role); AI Copilot appeared "broken" because a 502 from an
unconfigured/failing AI provider was silently discarded by the UI, not
because the wiring was broken; Global Search was traced end-to-end and
found to be dead, unwired UI backed by no page, hook, or API of any
kind (not a backend bug — nothing was ever built to be broken); eight
admin-only pages were reachable by any authenticated user via direct
URL despite being correctly hidden from the sidebar, because the route
guard mechanism (RoleGuard) exists, is unit-tested, and works, but was
only ever applied once, non-restrictively, at the top of the route
tree. All of the above are now fixed. Two fully dead components and a
handful of silent-failure buttons were also found and fixed. No backend
files were touched — every fix was a frontend gap; the backend's own
authorization was already correct in every case checked.

## Findings

------------------------------------------------------------------
### 1. CRITICAL — Viewer completes assessment wizard before a 403
Root cause: `CreateAssessmentPage.tsx` / `CreateAssessmentForm.tsx` and
the `assessments/new` route had zero role/permission checks anywhere;
the only thing stopping a Viewer was the backend's `require_analyst`
dependency on `POST /assessments`, discovered only after 4 wizard steps.
Evidence: `src/kingsec/adapters/inbound/web/routes.py:394` requires
`Role.ANALYST`; `frontend/src/routes/index.tsx` had no `RoleGuard` on
`assessments/new`; `frontend/src/pages/AssessmentsPage.tsx:22` hides the
"New Assessment" *button* for Viewers but doesn't guard the route itself,
so direct navigation still reaches the wizard.
Files involved: frontend/src/routes/index.tsx
Minimal fix: wrapped the `assessments/new` route in the existing,
already-unit-tested `<RoleGuard roles={['analyst','admin']}>` component
(same mechanism the sidebar and one existing route already rely on) —
no new authorization code written, reused what was already there.
Verification performed: `tsc -b` clean, `RoleGuard`'s redirect behavior
already covered by `frontend/src/components/__tests__/RouteGuards.test.tsx`,
full vitest suite green, production build succeeds.
Regression risk: none — Analyst/Admin behavior is unchanged; only
Viewer's path to this one route changes (redirect to /unauthorized
instead of a wizard that always failed anyway).

------------------------------------------------------------------
### 2. HIGH — 8 admin-only pages reachable by any role via direct URL
Root cause: `Sidebar.tsx` correctly computes and enforces a `roles`
array per nav item (e.g. `roles: ['admin']` for Administration,
Identity, Backup, Audit Log, License, Deployment, Diagnostics,
Releases), but that filtering only controls what's *rendered in the
sidebar* — the actual routes for these pages in `routes/index.tsx`
carried no per-route `RoleGuard`, so a Viewer or Analyst who knows/
guesses the URL reaches the page component directly. The backend APIs
those pages call are correctly admin-gated, so no admin *data* leaks,
but the pages themselves load into broken/empty-permission-error states
for non-admins — inconsistent, confusing authorization UX and a real
gap versus what the sidebar visibly promises.
Files involved: frontend/src/routes/index.tsx (routes: administration,
identity, identity/:id, backup, backup/:id, audit, license, deployment,
diagnostics, release-audit)
Minimal fix: wrapped each of the 8 routes in `<RoleGuard roles={['admin']}>`,
mirroring exactly the roles array already declared for the same items
in `Sidebar.tsx` — no new restriction invented, just route-level
enforcement of what the sidebar already implies.
Verification performed: `tsc -b` clean, lint clean (warnings only, all
pre-existing), full vitest suite (257/257) green, production build
succeeds. Cross-checked every other nav item's backend role requirement
(Workers, Job Queue, Monitor/Dashboard, Threat Intel, Automation,
Scanner Discovery, Profiles) via grep of their route dependencies to
confirm none of them have a similar mismatch — confirmed all remaining
items are either genuinely open to all authenticated roles on the
backend (matching their sidebar visibility) or already correctly mixed
per-endpoint (e.g. Job Queue: read open to all, mutations admin-only).
Regression risk: none — Admin behavior is unchanged; Viewer/Analyst
now redirect to /unauthorized on these 8 URLs instead of loading a
broken page.

------------------------------------------------------------------
### 3. HIGH — AI Copilot "appears non-functional" — frontend swallows the error
Root cause: NOT a permissions issue, missing endpoint, missing DI
registration, or missing route — traced the full path (frontend →
`/copilot/ask` → mounted router → `CopilotService.ask()` → `AIQueryPort`
→ real `ExtendedAIAdapter`, all correctly wired). The AI subsystem is
deliberately "bring-your-own-key": `AISettings.api_key` defaults to
`None` (`src/kingsec/infrastructure/config/models.py:169`), so any
install without a configured provider key gets a proper
`AIAuthenticationError` -> HTTP 502 (`error_code: "KS-EXT-001"`) from
the backend — correct, intentional behavior, not a bug. The actual bug:
`AICopilotPage.tsx` called `askMutation.mutate(...)` but never read
`askMutation.error` anywhere — on failure the pending spinner just
disappeared with zero feedback, making a correctly-functioning-but-
unconfigured feature look completely broken.
Files involved: frontend/src/pages/AICopilotPage.tsx
Minimal fix: added an `onError` toast and a persistent inline error
banner reading `askMutation.error`, with a specific message
("AI provider is unavailable or not configured — check Settings")
when `errorCode === 'KS-EXT-001'`, generic message otherwise. Did not
touch the BYO-key backend design — that's intentional and correct.
Verification performed: `tsc -b` clean, full vitest suite green,
production build succeeds. (No dedicated AICopilotPage test file exists
in the suite to extend; the change is presentation-only, driven by an
existing TanStack Query mutation's already-correct error state.)
Regression risk: none — additive rendering only, no change to when/why
requests succeed or fail.

------------------------------------------------------------------
### 4. MEDIUM — Global Search is dead UI with no backend feature at all
Root cause: fully traced end-to-end. `Header.tsx`'s search `<Input>` had
no `value`/`onChange`/`onKeyDown`/form — a completely inert, uncontrolled
element that cannot call an API or navigate no matter what's typed.
There is no dedicated Search page, no `useGlobalSearch` hook, no
`searchApi.globalSearch()` client function, and no backend `/search`
endpoint anywhere — every "search" that exists in the codebase (assets,
attack-surface exposures, users, copilot conversations, plugin
marketplace) is entity-scoped and already correctly wired to its own
page, not to this header box. This is not a broken integration; it is
a control that was never implemented, classification: **dead UI, no
backend service**.
Files involved: frontend/src/components/layout/Header.tsx,
frontend/src/components/__tests__/Header.test.tsx
Minimal fix: per the standing "no redesign, no new features" constraint,
building a cross-entity global-search backend endpoint plus a new
frontend page and API client would be new scope, not a defect fix.
Instead made the control honest: disabled the input, changed its label/
placeholder to "coming soon", and gave it a tooltip explaining it isn't
available yet, so it no longer looks interactive while doing nothing.
Verification performed: `tsc -b` clean, vitest suite green (updated the
one assertion in Header.test.tsx to match the new label), build clean.
Regression risk: none. Remains an open product gap — see Remaining
Known Issues.

------------------------------------------------------------------
### 5. MEDIUM — Notification bell button had no click handler
Root cause: `Header.tsx`'s bell button rendered a permanent "unread"
red dot but had no `onClick` at all — clicking it did nothing, despite
a fully built `/notifications` route and `NotificationsPage` existing.
Files involved: frontend/src/components/layout/Header.tsx
Minimal fix: wired `onClick={() => navigate('/notifications')}`,
reusing the same `navigate` already used by the adjacent user-menu items
in the same file.
Verification performed: tsc/lint/vitest/build all clean.
Regression risk: none.

------------------------------------------------------------------
### 6. LOW — Silent-swallow error handling on 3 buttons
Root cause: `AICopilotPage.tsx`'s `handleExportMarkdown`/`handleExportJson`
ended in a `.catch(() => {})` with a comment admitting it was a
deliberate no-op; `AssessmentDetailPage.tsx`'s report-download button
only did `console.error(...)` on failure. In all three cases, a failed
click (expired auth, network error, 404) produces zero visible feedback
— the button appears to do nothing.
Files involved: frontend/src/pages/AICopilotPage.tsx,
frontend/src/pages/AssessmentDetailPage.tsx
Minimal fix: replaced each silent/console-only catch with
`toast.error(...)`, using the exact toast pattern already established
elsewhere in the app (e.g. `use-assessments.ts`).
Verification performed: tsc/lint/vitest/build all clean.
Regression risk: none — success paths unchanged.

------------------------------------------------------------------
### 7. LOW — 2 fully orphaned dead components
Root cause: `LoadingOverlay.tsx` and `FindingCard.tsx` had zero
production usage anywhere in the app — the only references to either
were their own dedicated unit tests, which test the orphan itself and
provide no coverage of anything else.
Files involved: frontend/src/components/shared/LoadingOverlay.tsx (+ test),
frontend/src/components/features/findings/FindingCard.tsx (+ test)
Minimal fix: deleted both components and their dedicated test files.
Confirmed via grep no barrel/index re-export referenced either name
after deletion.
Verification performed: full repo grep for both names returns zero
matches; vitest count dropped from 265 to 257 (exactly the 8 removed
tests, no other change); build/tsc/lint clean.
Regression risk: none — nothing else imported these.

## Remaining Known Issues

- **Global Search is unimplemented** (Finding #4). The header control
  is now honest about not being available rather than silently doing
  nothing, but no cross-entity search feature exists. Building one
  (backend aggregation endpoint + frontend page + hook) is new scope,
  intentionally not done this round.
- Two pre-existing, cosmetic-only generic error messages were noted but
  NOT changed (out of scope — not named in this round's findings, not
  broken, just less specific than the app's best-practice pattern
  elsewhere): `frontend/src/pages/AIAssistantPage.tsx:50-51` uses a
  generic toast instead of the underlying error text; `OrganizationSection.tsx`'s
  4 mutation-failure toasts don't interpolate `err.message` the way
  `use-assessments.ts` does.
- `ErrorState.tsx`'s default fallback text ("Something went wrong" / "An
  error occurred") is rarely hit (nearly all 24 real call sites pass an
  explicit message) — left as-is, it's a sane last-resort default, not
  a bug.
- One pre-existing, already-documented, unrelated backend test failure
  from prior phases remains untouched (not exercised this round since no
  backend files changed).

## Final Verdict

**Yes — KingSec can be shipped today.** Every concretely verified defect
from this round's findings (the Viewer wizard bypass, the 8 unguarded
admin routes, AI Copilot's silent failure, the 3 silent-swallow buttons,
2 dead components) is now fixed, tested, and does not touch Domain,
Application, or backend authorization at all. The one open item —
Global Search — is not a blocker: it was never a working feature to
begin with, and the fix applied makes the UI honest about that rather
than shipping a control that misleads users. No other blockers were
found across the authorization, integration, or code-quality passes
performed this round.
